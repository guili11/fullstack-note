### 二、索引体系（最核心板块，已彻底吃透）

select x  from table  where y

核心就是关注 x 是什么，y是什么。

MySQL 索引使用的核心原理
MySQL 使用 B+Tree 索引（最常见），特点是：

- 数据在磁盘上是 有序存储 的。
- 查询时会从根节点到叶子节点 二分查找。
- 只有满足 有序性 的条件才能利用索引，否则会退化成全表扫描。 B+Tree天然有序性
  所以，判断 SQL 是否能走索引的关键就是：WHERE 条件是否能利用索引的有序性。

1. 索引分类与本质

- 按「数据结构」分类：B+tree索引、Hash索引、Full-text索引。
- 按「物理存储」分类：聚簇索引（主键索引）、二级索引（辅助索引）。
- 按「字段特性」分类：主键索引、唯一索引、普通索引、前缀索引。
- 按「字段个数」分类：单列索引、联合索引。

1. 核心概念
   - 回表：二级索引→一级索引的二次查找过程
   - 覆盖索引：查询字段全在二级索引内，无需回表  （联合索引实现）
2. 核心规则
   - 最左前缀原则的底层原理
   - 四种查询性能排序：主键直查 > 覆盖索引 > 二级索引回表 > 全表扫描
   - 索引失效的常见场景
3. 实战设计
   - 个人项目索引搭建原则
   - 普通索引与覆盖索引的取舍
   - 联合索引的设计思路

##### 核心问题：哪个阶段会进入B+树拿数据？哪个阶段只操作拿出来的数据？

只有from和where阶段会进入B+树拿数据，其他阶段只操作拿出来的数据。（内存中）
所以说索引优化的核心就是，

1. 能不能让数据被被迅速查到 ，提高查询效率
2. 能不能让被查到的数据 利用索引天然有序性，省去后续排序、分组开销，从而提高操作效率。
   核心就是：少扫磁盘数据（全表扫描） + 少做内存重计算（排序，分组）
   一定记住 索引（B+tree）的天然有序性，我们对于索引的使用都是基于这一点的。
   总结：核心关注 二分查找：from where select 有序性： group by order by，这些阶段是可以用索引优化的，忘记为什么就想明白了再使用。
   过程：从B+树中读取到内存中，然后再操作数据
   从哪拿 → 先过滤 → 再分组 → 组过滤 → 选列 → 去重 → 排序 → 拿几条
   from join 拿到对应的B+树
   where 筛选出符合条件的记录   筛选过程中，索引加速
   group by，分组的目的，就是按照指定依据把数据划分成一个个独立组别，最终只提取**整组层面的统一特征**。
   having  分组后过滤，由于分组后，进入了组的层级， 所以只能按照 组的层级来筛选      ，组层级的特征是：聚合函数+组本身特征
   分组核心：绝对不允许使用 不是组层级的特征，例如按照班级分组了，就只能 使用班级层面的特征，例如总人数等，不能使用学生层面的数据，例如学生的名字

```
SELECT
class,
COUNT(*) AS 人数,
SUM(score) AS 总分,
AVG(score) AS 平均分,
MAX(score) AS 最高分,
MIN(score) AS 最低分,
GROUP_CONCAT(name) AS 全班姓名
FROM student
GROUP BY class;
```

核心的三个索引生效 类别  where select   group by order by

mysql优化器走索引的原则：
\=：精准捞一小部分数据 → 索引很香，必用
!=：剔除一小部分，捞绝大部分数据 → 索引性价比太低，直接放弃

索引 = 找「少量数据」最快
全表扫描 = 取「大部分数据」最快

核心：遵循B+树的结构，最左原则+天然有序性
where：
根据索引的结构，确定性，范围性，最左性。都会触发索引\
例如：= > <  in  between  like 'xx%'
不确定性，非最左性，非范围性， 无法利用有序性，需要全表扫描
例如：!= not in like '%xx'  is null
补充，多逻辑组合 and or not，not触发不了， and or 给索引就能触发。

总结：
基础：B+tree结构 + 优化器原则
分析 sql 语句 ，以及实际的数据量，然后判断怎么安排索引。
补充：争取 一个索引，适配多个sql语句。

     explain 定义：
   - 解释器会根据查询语句，生成一个执行计划，

| 字段             | 核心含义        | 常见取值优劣排序                          | 快速判断依据                                                                             |
| -------------- | ----------- | --------------------------------- | ---------------------------------------------------------------------------------- |
| type           | 访问类型，索引效率核心 | const > ref > range > index > ALL | ALL = 全表扫描最差；ref/const 最优；range 正常可用                                               |
| key            | 实际真正用到的索引   | 索引名 / NULL                        | 有索引名 = 生效；NULL = 索引失效                                                              |
| possible\_keys | 备选索引列表      | 索引名集合 / NULL                      | 仅参考，最终以 key 字段为准                                                                   |
| ref            | 索引匹配参照类型    | const、字段名、func                    | const 常量匹配性能最佳                                                                     |
| rows           | 预估扫描数据行数    | 数字越小越优                            | 行数越大，代表筛选效果越差，                                                                     |
| filtered       | 数据过滤有效率     | 0%\~100%                          | 百分比越高，筛选效果越好                                                                       |
| Extra          | 额外执行细节标识    | 优 / 劣标识区分                         | ✅ Using index：覆盖索引，无回表❌ Using filesort：额外文件排序❌ Using temporary：创建临时表（数据乱序了，需要重新排序） |

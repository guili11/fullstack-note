## 背景问题

### 查询慢（没有合适的二级索引时）

当表中数据量不断增长时，全表扫描的成本越来越高。假设一张表有 1000 万行数据，每行约 0.1KB，表大小约 1GB。一次全表扫描意味着把 1GB 数据从磁盘读到内存，查询响应时间从毫秒级退化到秒级甚至分钟级。

> 注：InnoDB 表一定有聚簇索引（主键索引）。这里的"查询慢"不是说完全没有索引，而是说**除了聚簇索引外没有合适的二级索引**来加速查询，导致只能遍历聚簇索引的所有叶子节点。聚簇索引在这里只起到了"存储数据"的作用，没有起到"加速查找"的作用。

### 子问题拆解

| 问题 | 答案 |
|------|------|
| **到底慢在哪？** | 主要慢在 **磁盘 IO**，而不是 CPU 计算 |
| **原有方案为什么不行？** | 全表扫描是顺序遍历 **O(N)**，数据量翻倍，耗时也翻倍，无法扩展 |

### 设计思路

```
突破口：减少数据访问量 + 变随机 IO 为顺序 IO
```

核心想法：如果能提前把数据"排好序"，查找时就不需要全部遍历，而是可以用**二分定位**快速找到目标数据的位置。这就是索引的原始动机。

## 前置理解

在进入索引原理之前，需要先理解 MySQL 在底层是如何组织和管理数据的。

### 前置知识链

```
你写 SQL 查询
  ↓
MySQL 是怎么执行这条 SQL 的？        → ① MySQL 如何执行一条查询
  ↓
存储引擎是怎么去磁盘捞数据的？         → ② 存储引擎如何读取数据
  ↓
如果没有（二级）索引，数据是怎么被扫出来的？ → ③ 什么是全表扫描
  ↓
InnoDB 底层以什么为单位存数据？        → ④ 什么是数据页（Page）
  ↓
磁盘 IO 为什么慢？顺序和随机有什么区别？ → ⑤ 磁盘 IO 基础知识
```

### MySQL 如何执行一条查询

一条 SQL 查询从发起到拿到结果，经历以下步骤：

```
SQL 语句
  ↓
① 连接器：建立连接、校验身份权限
  ↓
② 查询缓存（MySQL 8.0 已移除）：命中直接返回
  ↓
③ 分析器：词法分析、语法分析，生成解析树
  ↓
④ 优化器：决定使用哪个索引、选择 JOIN 顺序、生成执行计划
  ↓
⑤ 执行器：根据执行计划，调用存储引擎的接口
  ↓
⑥ 存储引擎（InnoDB）：在 B+Tree 中实际读写数据
```

> 索引相关的关键步骤在 **④ 优化器**（选择索引）和 **⑥ 存储引擎**（在 B+Tree 中查找）。

### 存储引擎如何读取数据

第 ⑥ 步"存储引擎读写数据"具体在做什么？简单说就是**去磁盘找数据，加载到内存，返回给执行器**。

```
执行器："查 idx_age 中 age=25 的记录"
  ↓
① 存储引擎去磁盘找到目标数据所在的页
  ↓
② 把页从磁盘加载到 buffer pool（内存缓冲池）
   ├── 可能是顺序 IO（范围查询时连续读多页）
   └── 可能是随机 IO（按条件跳着读不同位置的页）
  ↓
③ 在内存中处理数据（查找、比较、排序等），返回结果给执行器
```

至于"具体怎么找到目标页的"——那是 B+Tree 索引的查找机制，在后面的核心原理中展开。

| 问题 | 答案 |
|------|------|
| **buffer pool 是什么？** | InnoDB 的内存缓冲池，缓存磁盘页，避免每次查询都走磁盘 IO。可以理解为 MySQL 的"内存缓存层" |
| **一次磁盘 IO 读多少？** | 一页 = 16KB，这是最小值。但 InnoDB 可能预读（read ahead），一次读多页 |

### 什么是全表扫描

#### ① 先定性：它本质上就是顺序 IO

全表扫描就是 InnoDB 从聚簇索引（主键索引）的**第一个叶子节点开始，沿着双向链表顺序遍历所有叶子节点**，逐行检查是否满足 WHERE 条件。

```
全表扫描 = 遍历整棵 B+Tree 的所有叶子节点链表（顺序 IO）
```

- 因为是顺序遍历，所以是**顺序 IO**——磁头连续读，几乎无需寻道
- 数据量越大，扫描的页越多，总 IO 时间越长

#### ② 什么时候发生全表扫描？

| 场景 | 原因 |
|------|------|
| **没有合适的二级索引** | WHERE 条件没有对应索引，优化器只能走聚簇索引全扫 |
| **索引失效** | 有索引但查询写法导致用不了（如隐式转换、LIKE `%xxx`） |
| **优化器认为全表扫描更快** | 分两种情况：① **表很小**（几百行）→ 全表扫描就很快，没必要走索引；② **表很大但索引过滤效果差** → WHERE 条件匹配了太多行，还不如顺序扫全表划算 |
| **查询需要处理大部分数据** | 如 `SELECT COUNT(*)`、没有 WHERE 条件的查询 |

#### ③ 全表扫描是坏事吗？

```
不全是。取决于场景：

❌ 大表 + 只查少量数据 → 灾难（应该走索引）
✅ 小表（< 1000 行）    → 可以接受，甚至比走索引快
✅ 需要处理大部分数据   → 全表扫描就是最优解
```

很多人的误区是"一看到 `type = ALL` 就觉得有问题"。其实优化器不傻，它选择全表扫描一定有它的理由——要么是表太小，要么是你需要的数据本身就占了大部分。

#### ④ 开发中怎么对待？

| 原则 | 说明 |
|------|------|
| **不是见 ALL 就杀** | EXPLAIN 看到 `type = ALL`，先看 `rows`。小表全表扫描不用管 |
| **大表要警惕** | 百万级以上的表出现全表扫描，大概率需要加索引或改写 SQL |
| **结合 WHERE 条件看** | 如果 WHERE 筛选后只返回少数行，却走了全表扫描，那就是索引没设计好 |
| **最终标准是延迟** | 用户不觉得慢，全表扫描也无所谓；用户觉得慢，就要优化 |

### 什么是数据页（Page）

InnoDB 以**页（Page）**为单位管理磁盘数据，一次磁盘 IO 读写一整页。

```
Tablespace → Segment → Extent（1MB = 64页） → Page（16KB） → Row
```

| 问题 | 答案 |
|------|------|
| Page 多大？ | 16KB，这是 InnoDB 磁盘 IO 的最小单位 |
| 一页能存多少行？ | 取决于行大小，假设每行 200B，一页 ≈ 80 行 |
| 页内如何组织？ | Page Header + Infimum/Supremum + User Records + Page Directory |
| 页目录是干嘛的？ | 页内的"稀疏索引"，通过二分查找快速定位槽位，再遍历槽内记录 |
| 为什么 16KB？ | 折中：太大浪费内存和缓冲池，太小导致 IO 次数过多 |
| 行溢出怎么处理？ | TEXT/BLOB 等大字段单独存到溢出页，行内只保留 20 字节指针 |

### 磁盘 IO 基础知识

理解索引为什么快，先要知道磁盘 IO 的基本规律。

| 问题 | 答案 |
|------|------|
| **为什么要读到内存？** | CPU 只能处理内存中的数据，磁盘数据必须加载到内存才能被计算。这是冯·诺依曼体系决定的 |
| **为什么要追求少磁盘 IO？** | 磁盘 IO 是数据库最慢的操作（寻道 ≈ 10ms），而内存操作快 10 万倍。减少 IO 次数 = 直接缩短查询时间。索引的一切设计都是围绕"用尽量少的 IO 找到目标数据" |
| **什么是随机 IO 和顺序 IO？** | 顺序 IO：磁盘磁头连续读写，几乎无需寻道，效率高（如全表扫描）。<br>随机 IO：数据分散在不同位置，每次读写都要寻道（≈10ms），效率低（如按主键逐行查）。<br>**关键理解**：数据库优化的本质就是"把随机 IO 变成顺序 IO" |
| **MySQL 中分别什么时候发生？** | **顺序 IO**：全表扫描、范围查询（叶子节点链表连续遍历）、redo log 顺序写入、binlog 顺序写入。<br>**随机 IO**：回表（根据主键逐行回聚簇索引查）、二级索引查单行、DML 修改分散在不同页的数据 |

## 核心原理

### 为什么索引能解决查询慢的问题

根据前置知识，我们知道：

```
查询慢 → 慢在磁盘 IO 次数太多
磁盘 IO 次数 → 取决于要扫描多少数据（多少页、多少行）
所以核心目标就是：减少扫描的行数
```

索引解决这个问题的逻辑链：

```
没有索引时：
  全表扫描 → 扫描 N 行 → N 次 IO（或更多） → 慢

有索引时：
  索引是排好序的结构 → 可以二分查找 → O(log N) 定位目标行
  → 只需扫描少量行 → 只需少量磁盘 IO → 快
```

举个最简单的例子：

```
表 users 有 1000 万行，查 age = 25

没有索引（全表扫描）：
  从上往下扫 1000 万行，逐行比对 age = 25
  → 扫描 1000 万行 → 假设每页 80 行 → 读 12.5 万页
  
有索引 idx_age（B+Tree）：
  从根节点二分查找 → 3 层就能定位到 age=25 的叶子节点
  → 扫描 3 页就找到了 → 最多 3 次 IO
```

换个更直观的说法：

```
没有索引 = 在一本书里逐页翻，直到找到你要的内容
有索引    = 先查目录（索引），直接翻到对应的页码
```

但索引不是免费的：

```
代价 = 空间换时间
   ↓
   - 索引占用额外磁盘空间
   - 写入（INSERT/UPDATE/DELETE）需要同时维护索引，DML 变慢
```

### InnoDB 索引结构：B+Tree

上一节说了，索引的核心是靠"有序结构 + 二分查找"来加速。那么问题来了：**MySQL 到底用了什么样的数据结构来实现这个"有序"？**

#### 需求分析：我们需要什么样的结构？

```
我们对索引结构的要求：
  ① 数据要有序 → 才能二分查找
  ② 能支持范围查询（>、<、BETWEEN）
  ③ 尽可能矮 → 减少磁盘 IO（树越高，IO 次数越多）
  ④ 写入效率也要能接受
```

那就看看常见的几种数据结构，哪个最符合这些需求。

#### 方案对比：为什么一定是 B+Tree？

| 对比方案 | 为什么不行 |
|----------|-----------|
| **哈希表** | 只支持等值查询（`=` `IN`），不支持范围查询（`>` `<` `BETWEEN`），无法排序 |
| **二叉树** | 树高 O(log₂N)，1000 万行 ≈ 24 层，每层一次 IO，24 次 IO 太慢 |
| **B-Tree** | 非叶子节点也存数据，一页能存的键值变少 → 树变高，IO 次数增多 |
| **B+Tree** ✅ | 非叶子节点只存键（不存数据）→ 一页能存约 1170 个键 → 3 层就能存约 **2200 万行** |

#### 设计原则：为什么这样设计

B+Tree 的一切设计都围绕一个目标：**让树尽可能矮**。那怎么做到矮？

```
树的层数 ≈ 总数据量 / 每个非叶子节点能装的键数

每个节点 = 一页（16KB）
一页能装的键越多 → 分支越多 → 树越矮 → IO 越少
```

所以核心设计就是：**非叶子节点只存键，不存数据**。

对比一下就清楚了：

```
B-Tree（非叶子节点也存数据）：
  一页 16KB，假设一行数据 200B，键值 8B
  一页能装 ≈ 80 行（数据占了大部分空间）
  1000 万行 → 需要更多层 → IO 更多

B+Tree（非叶子节点只存键）：
  一页 16KB，一个键值对（8B 键 + 6B 指针）= 14B
  一页能装 ≈ 1170 个键
  3 层就能存 1170² × 16 ≈ 2200 万行
```

设计原则总结：

```
B+Tree 设计原则：
  ① 节点尽可能宽（一页装尽可能多的键）→ 树更矮 → 定位 IO 更少
  ② 叶子节点用链表串联 → 范围遍历是顺序 IO → 高效
  ③ 非叶子节点只存键不存数据 → 节点更宽 → 树更矮（与原则 ① 呼应）
```

#### 核心结构

```
非叶子节点：只存 [键值 + 子节点指针]
叶子节点： 存 [完整数据行（聚簇索引）] 或 [主键值（二级索引）]
叶子节点：用双向链表串联 → 范围查询 = 沿着链表顺序遍历 = 顺序 IO
```

#### 插入与页分裂（写入维护）

```
插入过程：
① 根据键值找到目标叶子节点位置
② 如果叶子节点有空间 → 直接插入
③ 如果叶子节点已满 → 页分裂（申请新页，挪一半数据过去）
④ 更新父节点指针 → 如果父节点也满了，继续向上分裂

页分裂的代价：
- 移动数据 + 更新指针
- 产生磁盘碎片
- 写入变慢

为什么建议自增主键？
- 自增主键插入时总是"最右边" → 不会触发页分裂
- UUID 作为主键 → 随机插入 → 频繁页分裂 → 写入性能差
```

### B+Tree 如何查找数据

上一节介绍了 B+Tree 的结构。这一节来看：**有了这个结构，我们怎么用它来查找数据？**

B+Tree 查找数据分两个阶段，各自解决的 IO 问题不同。

#### 阶段一：定位（树遍历）—— 解决"找到起点"

等值查询 `WHERE age = 25` 的定位过程：

```
第 1 次 IO：加载根节点页
  在页内通过页目录二分查找，找到 age=25 应该去哪个子节点
  ↓
第 2 次 IO：加载第 2 层节点页
  在页内再次二分查找，找到 age=25 应该去哪个子节点
  ↓
第 3 次 IO：加载叶子节点页
  在页内通过页目录二分查找，定位 age=25 的具体记录位置
  ↓
找到目标数据
→ 总共 3 次 IO（3 层 B+Tree）
→ 树越矮，IO 越少
```

范围查询 `WHERE age > 25` 的定位过程也一样：从根节点开始，逐层二分查找，找到第一个 `age > 25` 的叶子节点，也是 **3 次 IO**。

> 注意：每一层都要把对应的页从磁盘读到内存（如果 buffer pool 没命中），然后在页内用二分查找确定下一步。所以**树高 = 定位阶段的 IO 次数**。

#### 阶段二：遍历（链表遍历）—— 解决"扫出范围"

```
WHERE age > 25（范围查询）：
  找到起点后，顺着叶子节点的双向链表往后遍历
  → IO 次数 = 范围内涉及的叶子节点页数
  → 这是顺序 IO，效率高
```

#### 两种查询的总 IO 对比

```
等值查询 age = 25：
  总 IO = 树高（3 次 IO，且可能被 buffer pool 缓存）
  → 不管表多大，几乎恒定

范围查询 age > 25：
  总 IO = 树高（定位起点）+ 范围内叶子节点页数（顺序遍历）
  → 定位部分恒定（3 次），遍历部分取决于数据量
```

> **关键理解**：B+Tree 用"树遍历"解决定位问题（矮 → 少 IO），用"链表遍历"解决范围问题（顺序 IO → 高效）。两个阶段合在一起，覆盖了等值和范围两种查询场景。

#### 回表与覆盖索引

回表是二级索引特有的概念：

```
二级索引的叶子节点只存 [索引列 + 主键值]，不存完整数据行

所以当你用二级索引查到记录时：
  ① 先拿到主键值（如 id=10）
  ② 再拿主键去聚簇索引查完整数据（这个过程就叫"回表"）
```

回表的代价：

```
找到 N 条满足条件的记录 → 回表 N 次
每次回表 = 1 次随机 IO（在聚簇索引的 B+Tree 中再查一次）
→ 这就是为什么"少用 SELECT *"的原因之一
```

覆盖索引是"不回表"的优化：

```
如果查询的列全部在二级索引中 → 不需要回表 → Extra 显示 "Using index"

例：索引 (age, name)，查询 SELECT age, name FROM users WHERE age = 25
  → 二级索引叶子节点就有 age 和 name，直接返回
  → 省掉了回表的那次随机 IO
```

> **关键理解**：二级索引 = 先定位（树遍历）+ 可能回表（随机 IO）。覆盖索引 = 定位完就直接返回，省掉回表。这就是为什么设计索引时尽量把查询列包含进去。

## 工程实践

### EXPLAIN：验证索引是否生效

```sql
EXPLAIN SELECT * FROM users WHERE age = 25;
```

| 字段 | 怎么看 |
|------|--------|
| **type** | `system > const > eq_ref > ref > range > index > ALL`<br>看到 `ALL` 就是全表扫描，需要优化 |
| **key** | 实际用到的索引名，`NULL` 表示没走索引 |
| **rows** | 预估扫描行数，越小越好（从 1000 万变成 100，就是好索引） |
| **Extra** | `Using index` ✅ 覆盖索引<br>`Using filesort` ❌ 需要优化排序<br>`Using temporary` ❌ 需要优化分组 |

### 最左前缀原则

```
联合索引 (a, b, c) 相当于建立了三个索引：
  - (a)
  - (a, b)
  - (a, b, c)

查询条件必须从最左边开始，跳过某列会导致后面的列无法使用索引。
```

### 索引设计原则

| 原则 | 说明 |
|------|------|
| **区分度高的放前面** | 唯一值多的列优先（如用户 ID > 性别） |
| **等值查询放前面** | `WHERE a=1 AND b>2` → (a, b)，a 在前面 |
| **范围查询放最后** | 范围条件会导致后面的列索引失效（范围截断） |
| **优先覆盖索引** | 查询字段尽量都在索引中，避免回表 |
| **不建过多索引** | 索引占用空间 + DML 变慢 + 优化器可能选错 |

### 索引失效场景（面试高频）

| 场景 | 示例 | 原因 |
|------|------|------|
| 隐式类型转换 | `WHERE id = '123'`（id 是数值） | MySQL 会对 id 做函数转换 |
| 对索引列用函数 | `WHERE DATE(create_time) = '2024-01-01'` | 索引存的是原始值，不是函数结果 |
| LIKE 左模糊 | `WHERE name LIKE '%张'` | 无法确定起始位置 |
| OR 含非索引列 | `WHERE a=1 OR b=2`（b 没索引） | 必须全表扫描才能处理 b 的条件 |
| 联合索引违反最左前缀 | 索引 (a, b)，查询 `WHERE b=1` | 跳过了最左列 a |
| != / <> / NOT IN | `WHERE status != 1` | 无法在有序结构中确定范围边界 |
| 数据量太小 | 表只有几十行 | 优化器认为全表扫描比走索引更快 |

## 示例与注意事项

### 案例一：多条件查询优化

```sql
-- ❌ 慢查询：全表扫描
SELECT id, order_no, amount
FROM orders
WHERE user_id = 100 AND create_time > '2024-01-01'
ORDER BY create_time DESC
LIMIT 20;

-- EXPLAIN: type = ALL, rows = 500万

-- ✅ 优化：建联合索引 (user_id, create_time)
ALTER TABLE orders ADD INDEX idx_user_time (user_id, create_time);

-- 为什么有效？
-- ① user_id 等值 → B+Tree 定位到该用户的所有记录
-- ② create_time 范围 → 索引天然有序，无需 filesort
-- ③ 如果要进一步优化到覆盖索引，把 order_no, amount 也加到索引中
```

### 案例二：深分页问题

```sql
-- ❌ 慢查询：OFFSET 1000000 意味着要先扫描 100 万行再丢弃
SELECT * FROM articles ORDER BY id LIMIT 20 OFFSET 1000000;

-- ✅ 优化：游标分页（记住上一页最后一条的 id）
SELECT * FROM articles WHERE id > 1000000 ORDER BY id LIMIT 20;

-- ✅ 或：子查询延迟关联（先走覆盖索引定位 id，再回表）
SELECT * FROM articles
WHERE id IN (
  SELECT id FROM articles ORDER BY id LIMIT 20 OFFSET 1000000
);
```

### 案例三：覆盖索引避免回表

```sql
-- 表有索引 (status, create_time)

-- ❌ 回表：SELECT * 需要所有列，二级索引不够用
SELECT * FROM orders WHERE status = 1;

-- ✅ 不用回表：查询列全部在索引中
SELECT status, create_time FROM orders WHERE status = 1;
-- Extra: Using index（覆盖索引）
```

### 面试高频追问

| 问题 | 核心回答 |
|------|---------|
| 为什么 MySQL 用 B+Tree 不用 B-Tree？ | B-Tree 的非叶子节点也存数据，一页能存的键更少，树更高，IO 更多 |
| 主键用自增 ID 还是 UUID？ | 自增 ID。UUID 无序插入导致频繁页分裂，插入性能下降，且索引碎片多 |
| 联合索引 (a, b) 和 (b, a) 一样吗？ | 不一样。前者 `WHERE a=1` 走索引，后者 `WHERE a=1` 不走。取决于查询条件 |
| 为什么有时候有索引却不用（type = ALL）？ | 优化器判断全表扫描更优：数据量太小、或者扫描行数占比太高（超过约 20%） |
| 唯一索引和普通索引怎么选？ | 写多读少选普通索引（可用 change buffer）；唯一性校验是刚需才选唯一索引 |

### 交叉链接

| 关联知识 | 关联点 |
|----------|--------|
| **间隙锁** | 在索引间隙上加锁。如果查询没有索引，间隙锁升级为表锁，并发下降 |
| **MVCC + undo log** | 二级索引的可见性判断需要回表查聚簇索引中的隐藏列 `DB_TRX_ID` |
| **change buffer** | 唯一索引插入时必须校验唯一性，不能用 change buffer；普通索引可以用 |
| **filesort** | ORDER BY 不走索引时触发，可能使用内存排序或归并排序（临时文件） |
| **自适应哈希索引（AHI）** | MySQL 自动为高频等值查询的 B+Tree 构建哈希索引，对用户透明 |
| **索引下推（ICP）** | MySQL 5.6+，把 WHERE 条件下推到存储引擎层过滤，减少回表次数 |

## 什么是 MySQL 中的事务？


**标准定义**：事务是数据库**执行逻辑的最小工作单元**，一组 SQL 操作要么**全部成功提交（COMMIT）**，要么**全部失败回滚（ROLLBACK）**，不存在"执行到一半"的中间状态。

### 事务的核心功能：回滚

事务最核心的功能就是**回滚**——只要事务还没提交，你可以随时放弃本次所有修改，数据库恢复原状。 以及 出现系统错误，mysql会自动回滚事务。

```sql
START TRANSACTION;

UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;

-- 发现 B 账号有问题，想放弃这次转账
ROLLBACK;  -- ✅ A 的 100 元也恢复原状，数据库回到转账前的状态
```

### 典型例子（转账）

```sql
-- 转账：A 扣 100 元，B 加 100 元
-- 这两条 SQL 必须打包成一个事务，不能一个成功一个失败

START TRANSACTION;

UPDATE account SET balance = balance - 100 WHERE id = 1;  -- A 扣钱
UPDATE account SET balance = balance + 100 WHERE id = 2;  -- B 加钱

COMMIT;  -- ✅ 两条 SQL 一起提交，一起成功
```

**如果不加事务：** 第一条 SQL 执行完（A 扣了 100），第二条 SQL 执行失败（B 没收到钱），100 块钱凭空消失了。

**加上事务：** 如果中途断电/崩溃/出错，MySQL 自动执行 ROLLBACK，A 扣掉的钱也恢复原状，一分不少。

---

**一句话总结：** 事务就是一个"后悔药"——要么全部做完（COMMIT），要么回到起点（ROLLBACK），不存在改一半的状态。

## 事务的四大特性（ACID）

为什么需要 ACID？因为数据库在执行一组操作时，会遇到四个现实问题。

### 场景：转账（A 扣 100，B 加 100）

```sql
START TRANSACTION;

UPDATE account SET balance = balance - 100 WHERE id = 1;  -- 第 1 步
UPDATE account SET balance = balance + 100 WHERE id = 2;  -- 第 2 步

COMMIT;
```

### 问题 1：第 1 步执行完，第 2 步还没执行，数据库崩了怎么办？

**A（原子性 Atomicity）来解决**

原子性保证：**要么全部做完（COMMIT），要么全部回滚（ROLLBACK），不存在执行一半的中间状态。**

- 实现手段：**Undo Log**（回滚日志）。每条修改操作执行前，先把"修改前的值"记到 Undo Log 里。如果事务失败，通过 Undo Log 恢复原状
- 例子：A 扣了 100 后崩了 → 靠 Undo Log 把 A 的余额改回原来的值

### 问题 2：事务提交后，数据库突然宕机了，改好的数据会不会丢？

**D（持久性 Durability）来解决**

持久性保证：**一旦 COMMIT，数据的修改就是永久的，不会因为宕机而丢失。**

- 实现手段：**Redo Log**（重做日志）。提交事务时，先把修改操作写入 Redo Log（顺序写，很快），然后再写数据文件。宕机重启后，从 Redo Log 里把没来得及写进数据文件的修改重新执行一遍
- 例子：转账成功 COMMIT 后断电 → 重启后靠 Redo Log 恢复，B 的余额依然是加过 100 的

### 问题 3：事务 A 在改，事务 B 同时来读，B 读到了改到一半的数据怎么办？

**I（隔离性 Isolation）来解决**

隔离性保证：**多个事务并发执行时，互不干扰，每个事务感觉像在独占执行。**

- 实现手段：**锁 + MVCC（多版本并发控制）**
- 例子：A 正在转 100 元（还没提交），B 查询余额。隔离性保证 B 不会读到 A 改到一半的数据

### 问题 4：事务改完数据后，数据不符合业务规则了怎么办？

**C（一致性 Consistency）来解决**

一致性保证：**事务开始前和结束后，数据都必须符合业务规则（约束、触发器、业务逻辑等）。**

- 数据库通过约束（唯一键、外键、非空）辅助保证；业务逻辑靠开发者保证
- 例子：A 扣了 100 但 B 没加 100 → A + B 总和变了，数据就不一致了

### ACID 的关系

```
A（原子性） + I（隔离性） + D（持久性）
        ↓
  共同保障 C（一致性）
```

**C（一致性）是最终目标，A、I、D 是手段。** 事务不会半途而废（A）、不会互相干扰（I）、不会丢数据（D），数据自然就一致（C）了。

### ACID 的保障分工

| 特性 | MySQL 底层自动保障 | 开发者需要保障 |
|------|------------------|--------------|
| **A（原子性）** | ✅ Undo Log 自动记录和回滚 | 无，只需要写 `COMMIT` / `ROLLBACK` |
| **I（隔离性）** | ✅ 锁 + MVCC 自动处理 | 无，只需要选隔离级别（默认 RR） |
| **D（持久性）** | ✅ Redo Log 自动写盘恢复 | 无，MySQL 自己保证 |
| **C（一致性）** | ❌ 只能辅助（唯一键、外键、非空约束） | **核心靠开发者**：业务逻辑要正确（如 A 扣 100，B 必须加 100） |

**A、I、D 你基本不用操心，MySQL 自己就干了。C（一致性）才是你写代码时需要保证的部分。**

## 隔离级别（I 的具体实现）

隔离性要解决的核心问题是：**多个事务并发执行时，互相能读到什么程度的数据？**

聚焦 写的时候，怎么读   别的读写冲突，看后续的锁笔记

### 并发问题（三种异常现象）

| 问题 | 描述 | 举例 |
|------|------|------|
| **脏读** | 读到了其他事务**未提交**的数据 | A 改数据但还没 COMMIT，B 就读到了 |
| **不可重复读** | 同一事务内，**多次读取同一条数据**，结果不一样 | 第一次读 balance=100，第二次读 balance=200（被其他事务改了） |
| **幻读** | 同一事务内，**同一条件查询**，两次查到的行数不一样 | 第一次查到 5 条，第二次查到 6 条（其他事务插入了新数据） |

**为什么要解决不可重复读？**  
可重复读保证的是：事务内所有读操作看到的是同一个「时间点的快照」，让事务能够在一个「稳定的数据视图」上完成所有业务逻辑，而不是在一个不断变化的数据上左右摇摆。

**幻读跟可重复读的区别？**  
- **可重复读**是一个目标/保证：事务内多次读取同一条数据，结果永远一样
- **幻读**是一个并发问题（一种具体的问题现象）：同一个条件查询，两次查到的行数不一样（多了或少了新插入的数据）

---

### 四大隔离级别

| 隔离级别 | 解决的问题 | 存在的问题 | 说明 |
|----------|----------|----------|------|
| **读未提交（RU）** | 无 | 脏读、不可重复读、幻读 | 最低级别，实际不用 |
| **读已提交（RC）** | 脏读 | 不可重复读、幻读 | Oracle 默认级别 |
| **可重复读（RR）** | 脏读、不可重复读 | 幻读（间隙锁可解决） | **InnoDB 默认级别** |
| **串行化（Serializable）** | 全部解决 | 无 | 不支持并发，实际不用 |

> 注：Redis 用串行化 + IO 多路复用实现了高并发，但与 MySQL 的串行化隔离级别不是一回事，不要混淆。

---

### 实现原理：锁 + MVCC

隔离级别的底层实现靠两个核心机制：**锁** 和 **MVCC（多版本并发控制）**

#### 1. MVCC 是什么？

MVCC 就是「**读不改锁**」——通过维护数据的多个版本来实现，允许你"读旧版本"而不去抢锁，实现了读和写可以同时进行。

**没有 MVCC**：读和写互斥，并发性能差  
**有 MVCC**：读可以读旧版本，不用等写操作释放锁

mvcc工作原理： 核心关注  read view的创建时机   


#### 2. MVCC 如何跟锁搭配实现隔离？

| 读类型 | 场景 | 实现方式 |
|--------|------|----------|
| **快照读** | 普通 `SELECT` | 走 MVCC，不加锁，读历史版本 |
| **当前读** | `UPDATE` / `DELETE` / `SELECT ... FOR UPDATE` | 走锁，必须拿到最新数据 |

#### 3. 各隔离级别的锁策略

| 隔离级别 | 写操作 | 读操作 |
|----------|--------|--------|
| **读未提交** | 写加锁（行锁） | 读不加锁 |
| **读已提交** | 写加锁（行锁） | 读用 MVCC，无间隙锁 |
| **可重复读** | 写加锁（行锁 + 间隙锁） | 读用 MVCC |
| **串行化** | 读写都加锁（行锁 + 间隙锁 + 读锁） | 读写都加锁 |

#### 4. RC 和 RR 的 MVCC 快照时机不同

**为什么读已提交（RC）使用了 MVCC，但没有解决不可重复读？**

| 隔离级别 | 快照生成时机 | 效果 |
|----------|------------|------|
| **读已提交（RC）** | 每次 `SELECT` 都生成新快照 | 能读到其他事务已提交的数据 → 不可重复读 |
| **可重复读（RR）** | 事务开始时生成一次快照，后面复用 | 整个事务读同一份快照 → 解决不可重复读 |

> 当 RR 级别下想读最新版本数据时，使用 `SELECT ... FOR UPDATE` 走锁机制（当前读）

### InnoDB 如何解决幻读？

幻读的本质：**两次读的数据不一致**，分两类场景解决：

| 场景 | 解决方式 | 原理 |
|------|----------|------|
| **快照读**（普通 `SELECT`） | MVCC | 事务内读同一份快照，根本看不到新数据 |
| **当前读**（`FOR UPDATE` / `UPDATE` / `DELETE`） | 间隙锁（Gap Lock） | 锁住范围，禁止新数据插入 |

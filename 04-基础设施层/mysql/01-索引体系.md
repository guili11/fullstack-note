# MySQL 索引体系

## 一、B+树原理

### 为什么用 B+ 树做索引？
- 数据在磁盘上**有序存储**
- 查询时从根节点到叶子节点**二分查找**
- 只有满足**有序性**的条件才能利用索引，否则退化成全表扫描

### 核心特性
- 矮胖结构：3-4 层就能查到数据，减少磁盘 IO
- 叶子节点链表：天然有序，范围查询高效
- 非叶子节点只存索引键：单页能存更多键值，树更矮

---

## 二、索引分类

### 按数据结构
- B+Tree 索引（最常用）
- Hash 索引
- Full-text 全文索引

### 按物理存储
- **聚簇索引**（主键索引）：叶子节点 = 完整数据行
- **二级索引**（辅助索引）：叶子节点 = 索引值 + 主键值

### 按字段特性
- 主键索引、唯一索引、普通索引、前缀索引

### 按字段个数
- 单列索引、联合索引

### 索引类型速查表

| 索引类型 | 定位 | 使用场景 |
|----------|------|----------|
| 主键索引 | 基础核心，InnoDB 聚簇索引 | 每张表必带，查询主键速度最快 |
| 普通单列索引 | 简单单条件查询 | 只有单个查询条件时使用 |
| 唯一索引 | 约束 + 查询双重作用 | 手机号、账号这类不能重复的字段 |
| 全文索引 | 文本模糊检索 | 文章、内容大段文字搜索，替代低效 like %% |
| 空间索引 | 地理位置专属 | 经纬度、地址距离查询，业务小众 |
| **联合索引** | **多条件组合查询** | **业务最常用，覆盖多个查询条件** |

---

## 三、核心概念

### 回表
二级索引查到主键值 → 再去主键索引找完整数据行

### 覆盖索引
查询字段全在二级索引内，无需回表（联合索引实现）

### 四种查询性能排序
主键直查 > 覆盖索引 > 二级索引回表 > 全表扫描

---

## 四、联合索引（核心）

### 核心本质
联合索引的字段先后顺序，直接决定 B+ 树内部数据的物理排序规则。

### 存储逻辑
联合索引 `(col1, col2, col3)`，不是三个单列索引简单拼接：
1. 优先按**第一个字段**全局排序
2. 第一个字段值相同，再按**第二个字段**排序
3. 第二个字段值相同，继续按**第三个字段**排序

**索引顺序 = 数据在磁盘 B+ 树里的物理摆放顺序**

### 最左前缀原则

因为数据是**从左到右层级排布**，查询只能顺着排布顺序匹配：

```
索引 (a, b, c)
where a=1 and b=2  ✅ 走索引
where a=1          ✅ 走索引
where b=2          ❌ 不走索引（跳过最左）
where c=3          ❌ 不走索引
```

### 范围查询截断

一旦索引中某个字段做范围筛选，**该字段右边所有字段丧失索引检索能力**：

```
索引 (a, b, c)
where a=1 and b>10 and c=3
→ a 走索引 ✅
→ b 走索引 ✅（范围）
→ c 不走索引 ❌（范围右侧失效）
```

**原因**：范围区间内数据不再统一固定值，右侧字段原有排序被打乱。

### 字段顺序设计铁律

业务查询包含**等值、范围、分组、排序**时，索引字段按此顺序排布：

```
等值字段 → 范围字段 → 分组字段 → 排序字段
```

| 位置 | 字段类型 | 原因 |
|------|----------|------|
| 最左 | 等值字段 | 快速锁定固定区间，保留后续有序性 |
| 中间 | 范围字段 | 过滤数据，会破坏右侧全局有序性 |
| 末尾 | 分组/排序字段 | 复用索引原有顺序，减少额外排序 |

### 覆盖索引设计

把业务常用查询字段放在联合索引尾部：
- 查询需要的所有数据，直接在当前联合索引 B+ 树中就能拿到
- 不需要再跳转主键索引读取原始表数据，大幅减少磁盘 IO

## 五、索引失效场景

### 核心原则
索引 = 有序性 = 二分查找，任何破坏（不使用）有序性的操作都会导致索引失效！

| 场景 | 原因 | 举例 |
|------|------|------|
| 函数运算 | 需要对每个索引值执行函数才能判断 | `where year(create_time)=2026` |
| 隐式类型转换 | 类型不匹配，无法利用索引 | `where phone=1380000`（phone 是字符串） |
| `!=` / `NOT IN` | 剔除一小部分，捞绝大部分，索引性价比低 | `where status != 1` |
| `like '%xx'` | 前置模糊，无法利用有序性 | `where name like '%abc'` |
| `or` 连接无索引字段 | 整体索引失效 | `where a=1 or b=2`（b 无索引） |
| 跳过最左字段 | 破坏层级匹配 | `where b=2`（索引 a,b,c） |

### 优化器走索引的原则

```
=：精准捞一小部分数据 → 索引很香，必用
!=：剔除一小部分，捞绝大部分数据 → 索引性价比太低，直接放弃

索引 = 找「少量数据」最快
全表扫描 = 取「大部分数据」最快
```

### 会走索引的操作
`=`, `>`, `<`, `in`, `between`, `like 'xx%'`, `and`, `or`（有索引的字段）

### 不走索引的操作
`!=`, `not in`, `like '%xx'`, `is null`（数据量大时）, `not`

## 六、EXPLAIN 执行计划

### 定义
解释器根据查询语句生成执行计划，描述查询的执行顺序、使用的索引、扫描的行数等信息。

### 核心字段速查

| 字段 | 核心含义 | 常见取值优劣排序 | 快速判断依据 |
|------|----------|-----------------|-------------|
| type | 访问类型，索引效率核心 | const > ref > range > index > ALL | ALL = 全表扫描最差；ref/const 最优 |
| key | 实际真正用到的索引 | 索引名 / NULL | 有索引名 = 生效；NULL = 索引失效 |
| possible_keys | 备选索引列表 | 索引名集合 / NULL | 仅参考，最终以 key 字段为准 |
| ref | 索引匹配参照类型 | const、字段名、func | const 常量匹配性能最佳 |
| rows | 预估扫描数据行数 | 数字越小越优 | 行数越大，代表筛选效果越差 |
| filtered | 数据过滤有效率 | 0%~100% | 百分比越高，筛选效果越好 |
| Extra | 额外执行细节标识 | 优 / 劣标识区分 | ✅ Using index：覆盖索引，无回表<br>❌ Using filesort：额外文件排序<br>❌ Using temporary：创建临时表 |

## 七、SQL 执行顺序与索引优化

### SQL 逻辑执行顺序
```
FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

### 哪个阶段进 B+ 树拿数据？
**只有 FROM 和 WHERE 阶段会进入 B+ 树拿数据**，其他阶段只操作拿出来的数据（内存中）。

### 索引优化的核心
1. **少扫磁盘数据**（避免全表扫描）→ 二分查找
2. **少做内存重计算**（避免排序、分组）→ 利用索引天然有序性

| SQL 阶段 | 能否用索引优化 | 优化方式 |
|----------|---------------|----------|
| FROM/JOIN | ✅ | 选择合适的索引树 |
| WHERE | ✅ | 等值/范围过滤，索引加速 |
| GROUP BY | ✅ | 复用索引有序性，避免临时表 |
| ORDER BY | ✅ | 复用索引有序性，避免 filesort |
| SELECT | ✅ | 覆盖索引，避免回表 |
| HAVING | ❌ | 分组后过滤，内存操作 |
| LIMIT | ❌ | 内存操作 |

## 八、索引创建取舍原则

1. **高区分度字段优先建索引**
   - 性别、状态这类低区分度字段，不建议单独建索引
2. **不要冗余建索引**
   - 频繁增删改的表，索引越多，写入更新开销越大
3. **优先使用联合索引**
   - 一套联合索引可覆盖多条相似查询，利用率更高
4. **争取一个索引适配多个 SQL**
   - 分析表的所有高频查询，设计通用联合索引

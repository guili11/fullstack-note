# MySQL 索引核心使用原则总结

结合咱们实操+理论，整理成好记、可直接落地的规则，适配单索引、联合索引日常开发

## 一、联合索引核心基础规则

1. **最左前缀匹配原则**
   索引`(a,b,c)`，查询必须从最左侧字段开始匹配，不能跳过中间字段，否则后续字段无法走索引。
   例：能用`where a=1`、`where a=1 and b=2`；不能直接`where b=2`、`where c=3`。
2. **索引自带排序特性**
   联合索引按字段顺序依次排序，前缀匹配完成后，后续字段天然有序，可直接用于分组、排序。

## 二、联合索引字段设计排序铁律

业务查询包含**等值、范围、分组、排序**时，索引字段按此顺序排布：
**等值字段 → 范围字段 → 分组字段 → 排序字段**

- 等值放最前：快速锁定固定数据区间，保留后续字段有序性
- 范围放中间：过滤数据，会破坏右侧字段全局索引检索能力
- 分组、排序放末尾：尽可能复用索引原有顺序，减少额外排序开销

## 三、范围查询专属规则

1. 索引中某一字段做`> < >= <= between`范围筛选，**范围查询使右侧所有字段，丧失全局有序性**
2. 失效原因：范围拆分数据区间，单区间内字段有序，整体结果集无序，无法按索引层级查找
3. 兜底价值：即便右侧失效，前缀索引依旧能减少扫描行数，性能远优于全表扫描
4. 优化上限：范围卡在中间时，后续排序大概率触发`Using filesort`，无法彻底规避

## 四、查询语句避坑原则（防止索引失效）

**核心：索引 = 有序性 = 二分查找，任何破坏（不使用）有序性的操作都会导致索引失效！**

1. 索引字段避免使用函数运算、隐式类型转换
   反例：`where year(create_time)=2026`，索引直接失效    （MySQL需要对每个索引值执行函数才能判断）
2. 不等于`!= <>`、`not in`大概率不走索引，尽量改写查询逻辑
3. `like`模糊查询仅前缀匹配可用索引（`like 'abc%'`），后置、全模糊失效
4. `or`连接无索引字段，整体索引失效；`in`多值匹配可等效等值，不破坏有序性

## 五、索引创建取舍原则

1. **高区分度字段优先建索引**
   性别、状态这类只有少数固定值的低区分度字段，不建议单独建索引，容易触发全表扫描
2. 不要冗余建索引
   频繁增删改的表，索引越多，数据写入更新开销越大
3. 优先使用联合索引，少用零散单字段索引
   一套联合索引可覆盖多条相似查询，利用率更高

## 六、实用优化小原则

1. **覆盖索引优化**
   查询字段全部包含在索引内，无需回表查询主键数据，大幅提升查询速度
2. 排序、分组尽量依托索引原有顺序
   减少`Using filesort`、`Using temporary`临时计算开销
3. 小表无需刻意建索引
   数据量极少时，全表扫描成本低于索引查询，优化器会自动放弃索引

## 七、极简记忆口诀

前缀不能跳，等值放前头
范围断右侧，排序末尾留
字段少函数，模糊看开头
区分度优先，覆盖少回表

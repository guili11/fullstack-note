### MySQL 锁的粒度分类

| 锁粒度 | 锁类型 | 加锁方式 | 作用 | 使用场景 |
|--------|--------|----------|------|----------|
| **全局锁** | 全局读锁 | `FLUSH TABLES WITH READ LOCK` | 整个数据库只读，禁止增删改和表结构变更 | 全库逻辑备份（MyISAM 引擎必须用） |
| **表级锁** | 表锁（读锁/写锁） | `LOCK TABLES ... READ/WRITE` | 锁住整张表，限制其他会话的读写 | 简单场景的并发控制（InnoDB 不推荐用） |
| **表级锁** | 元数据锁（MDL） | 自动加锁，无需手动 | 防止 CRUD 时表结构被修改 | 所有表操作自动加锁，保证表结构安全 |
| **表级锁** | 意向锁（IS/IX） | 自动加锁，无需手动 | 快速判断表内是否有记录被加锁 | InnoDB 行锁的前置锁，避免遍历全表 |
| **表级锁** | AUTO-INC 锁 | 插入自增主键时自动加 | 保证自增主键连续递增 | 插入数据时使用主键自增时 |
| **行级锁** | 记录锁（Record Lock） | `SELECT ... FOR UPDATE` | 锁住单条记录 | 精确更新/查询某一行数据时 |
| **行级锁** | 间隙锁（Gap Lock） | RR 级别自动加 | 锁住索引间隙，防止插入新记录 | 解决幻读问题，防止其他事务插入数据 |
| **行级锁** | 临键锁（Next-Key Lock） | RR 级别自动加 | 记录锁 + 间隙锁，锁住范围+记录本身 | 范围查询时防止幻读 |
| **行级锁** | 插入意向锁 | INSERT 时自动加 | 表示插入意图，与间隙锁冲突 | 插入数据时检查是否被间隙锁阻塞 |

# innodb的锁策略？

InnoDB 的加锁策略可以用一句话总结：**能不加锁就不加锁，必须加锁时加最小粒度的锁**。

innodb加锁是加在 索引上的哦。   why？   innoDB是聚簇索引，锁只能加在 索引上，而且查询也方便。

行锁 ≠ 只锁修改的行，而是锁扫描过的所有行 。   为什么？  必须保证 扫描过程中的 一致性，避免扫描过程中有人修改扫描过的数据。     

当前读，为什么不走索引，就会导致 innodb锁全表？  

锁 目标数据可以理解，为什么要锁全表？

因为  必须保证 扫描过程中的 一致性，避免扫描过程中有人修改扫描过的数据。 

基于这一点，也可以知道，减少扫描的数据，可以减少加锁的花销和资源占用，  所以我们追究提高数据的 过滤性，减少扫描的数据量。

那么这里在读了，肯定就要加锁了， 那么innodb如何加锁呢？

| 查询条件 | 锁加在哪里 | 说明 |
|----------|-----------|------|
| `WHERE id = 1`（主键） | 主键索引 | 直接定位，只锁主键索引项 |
| `WHERE phone = '138'`（二级索引） | 二级索引 + 主键索引 | 二级索引上加锁，回表后主键索引也加锁 |
| `WHERE name = 'abc'`（无索引） | 主键索引（全表） | 全表扫描，每行的主键索引都加锁 |


### InnoDB 锁策略（按隔离级别）

#### RC 级别（读已提交）
- 普通 SELECT：MVCC 快照读，不加锁
- UPDATE/DELETE：只加 Record Lock（记录锁），锁命中的行（无法解决范围查询的幻读问题）
- 无间隙锁，不解决幻读

#### RR 级别（可重复读，默认）
- 普通 SELECT：MVCC 快照读，不加锁
- UPDATE/DELETE：加 Next-Key Lock（记录锁 + 间隙锁），锁行 + 锁间隙
- 有间隙锁，解决幻读

#### 通用规则（所有级别）
- 锁加在索引上，不是数据行上
- 行锁 ≠ 只锁修改的行，而是锁扫描过的所有行
- 必须走索引，否则全表扫描 = 全表加锁
- 意向锁自动加，不用管

核心思想就是：**用 MVCC 解决读冲突，用最小粒度行锁解决写冲突，用间隙锁解决幻读**。

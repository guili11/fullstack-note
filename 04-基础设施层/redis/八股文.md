## 一、Redis 为什么快？

前提，这里的快，就是指 一系列增删改查操作，执行的速度。
redis快的原因是，  内存， 单线程  配合单线程的 io多路复用

1. redis存在在内存中，数据读取很快，没有文件io开销。
2. 不需要处理文件io，所以可以使用单线程，没有线程切换开销
3. IO 多路复用让单线程能同时监听多个连接， 避免被单个连接阻塞 ，从而能 快速响应其他客户端的请求（这个请求就是别人已经发过来的增删改查的操作嘛）
4. 补充：底层数据结构极其高效

## 二、数据结构

区别，主要就看两点： 一个是 存的数据到底是什么   一个是 这个结构可以执行什么 数据操作
一个数据具体选择哪个数据结构呢？  分析这个数据是什么，以及我们需要对数据执行什么操作
redis 存储本质都是字符串（底层 SDS）

| 结构          | 存储内容             | 核心操作                                                     | 典型场景        | 注意事项                    |
| :---------- | :--------------- | :------------------------------------------------------- | :---------- | :---------------------- |
| **String**  | 字符串/数字/二进制       | `SET/GET` (基础读写)`INCR/DECR` (**原子自增**，无需加锁)              | 缓存、计数器、分布式锁 | 避免大 Key（>10KB）          |
| **List**    | 有序字符串列表（可重复）     | `LPUSH/RPOP` (**两端操作**，实现队列/栈)`LRANGE` (范围查询)            | 消息队列、朋友圈时间线 | 非阻塞用 List，阻塞队列用 `BLPOP` |
| **Set**     | 无序字符串集合（唯一）      | `SADD/SREM` (增删元素)`SINTER/SUNION` (**集合运算**，一行命令搞定交集/并集) | 标签、共同好友、抽奖  | 内存随元素增多，注意去重开销          |
| **ZSet**    | 有序集合（带 Score 分数） | `ZADD` (带分数添加)`ZRANGE` (**按排名查询**)`ZINCRBY` (**原子增加分数**) | 排行榜、延迟队列    | Score 可重复，Member 唯一     |
| **Hash**    | Field-Value 键值对  | `HSET/HGET` (**字段级读写**，不用拉取整个对象)`HINCRBY` (字段原子自增)       | 对象缓存、购物车    | go-redis 支持自动序列化 struct |
| **Bitmaps** | 位数组（0/1）         | `SETBIT/GETBIT` (**位级操作**)`BITCOUNT` (**统计 1 的个数**，极快)   | 签到、活跃用户统计   | 极致省内存，1 年签到仅 46 字节      |

**补充**：原子性操作 — 单线程模型保证命令执行不被打断。各数据结构提供无需加锁、天然线程安全的专属操作，高并发下性能极高。

## 三、TTL 设置

### 3.1 TTL 的影响

TTL 设置多少会影响什么？ 内存、性能与数据一致性。

TTL 拉太长，堆内存、脏数据久，倒逼内存淘汰频繁启动；
TTL 缩太短，丢命中率、炸数据库，过期删除 CPU 压力暴涨；
取值贴合业务更新频率，就能平衡内存、性能与数据一致性。

### 3.2 TTL 为什么贴合业务更新频率

因为缓存的目的是 提高访问速度，减少数据库压力 同时需要保持数据一致性。
只谈论数据库压力，肯定是ttl越长越好，但是这里带来的一个问题就是，数据一致性没有保障。
可以说，ttl 短，就是为了 数据一致性。越短，refresh频次越高，数据越fresh。

两个一致性情况：主要靠业务主动更新保障，缓存过期只是兜底手段。

- 缓存过期，引起的 mysql 开销
- mysql数据更新，引起的 缓存更新开销

两个开销不一样，但是目的都是为了数据一致性。ttl的作用就是缓存过期的兜底手段，不需要太过于纠结具体多少，根据更新频率去适配即可。

### 3.3 常见场景

- 秒杀、临时活动、验证码：秒 / 分钟级 TTL（几十秒～30 分钟），短期用完立刻失效
- 商品、资讯、首页通用缓存：1\~6 小时，兼顾新鲜度与访问命中率
- 用户基础资料、固定配置：半天～1 天，改动频率低，不用频繁过期重建

## 四、数据一致性

### 4.1 Cache Aside 方案

因为引入了redis，那么数据更新时，一个问题，先更新缓存，还是更新数据库？

理论上两个方案：

- 先更新数据库再处理缓存，是主流稳妥做法，契合版本号方案，能有效减少数据错乱问题。但是有 不一致窗口问题
- 先更新缓存再改动数据库，极易产生脏数据，业务开发中一般不会选用

**结论**：先更新数据库，再更新缓存。—— Cache Aside 方案

Cache Aside 方案：
先更新 数据库， 然后直接删除缓存， 等 下一次请求再新建缓存。

业务主动更新主要分为：

- 固定key，覆盖更新value
- 直接生成新 kv，覆盖旧kv，旧kv依赖 定时缓存+内存淘汰 删除

### 4.2 版本号方案

**为什么需要版本号？**

原有key组装简单，直接用业务id组装就可以了。但key更新时，需要让新数据替代旧数据。实现的方案就是版本号管理——版本号也是key的一部分，组装之前需要查询版本号，版本号本身也作为一个数据存储，最终的key就是依赖 版本号+业务id，达到新k的目的。

**版本号方案更新缓存的优点**

先思考，更新缓存的重要问题有哪些：本质：用单线程+原子性操作解决 高并发问题，而不是锁

1. 高并发下，在更新途中的不一致问题
2. 高并发下，更新缓存带来的缓存击穿问题。传统需要锁

优点：

- 无需手动删缓存，减少线上故障。更新k替代 删除k，incr原子性操作性能好
- 支持版本回滚与灰度发布
- 有效抵御缓存击穿、雪崩问题

**版本号方案流程**

修改数据，先incr版本号，让旧数据失效，然后写入mysql，然后再写入缓存。

**版本答案**

底层遵循通用的Cache Aside 旁路缓存大框架，写缓存统一用版本号方案实现。

- **读取流程**：先按版本号拼接 key 查缓存 → 没命中则查询数据库 → 把数据写入对应版本缓存
- **更新流程**：先修改数据库数据 → 生成全新版本 key 存入最新缓存 → 更新全局版本标记，后续请求自动切换读取新数据
- **旧数据处理**：无需手动删除，依靠 TTL 过期删除、LRU/LFU 内存淘汰机制自动回收即可

## 五、分布式锁

sync是内存级别的锁，不能跨服务器使用，redis是分布式锁，可以跨服务器使用。

加上 Double Check（重试机制）后的分布式锁核心步骤：

核心点：

- 加锁用 `SET NX PX`，解锁用 Lua 脚本
- 锁要设过期时间（防死锁），value 要带唯一标识（防误删）
- 自旋 + Double Check：先等一会 → 查缓存有没有被别的线程重建 → 没有才去抢锁
- 锁续期：业务耗时可能超过锁的过期时间，需要定时续命

1. **尝试加锁**：执行 `SET key value NX PX 30000`
   - `NX`：只有 key 不存在时才写入（互斥）
   - `PX 30000`：30 秒自动过期，防止锁忘记释放，必须有，避免死锁
   - `value`：存入唯一标识（如 UUID），用于解锁时校验身份，防止误删别人的锁
   - 加锁成功 → 执行第 3 步；加锁失败 → 进入第 2 步
2. **Double Check + 自旋重试**：加锁失败说明有其他实例持有锁，进入循环重试
   - **自旋等待**：短暂休眠（如 50\~100ms），避免 CPU 忙等
   - **Double Check**：休眠后**先检查缓存是否已被其他线程重建**（读缓存）。如果缓存已存在，说明持有锁的线程已经写完了，直接返回，无需再抢锁
   - **尝试加锁**：Double Check 发现缓存仍未命中，才去尝试加锁
   - **超时/重试退出**：设置总重试超时时间（如 3 秒），超过则放弃，防止请求长时间卡住
   - 重试成功 → 执行第 3 步；超时 → 返回失败
3. **执行业务逻辑**：持有锁期间执行临界区代码（如查 DB → 写缓存）
   - **锁续期**：如果业务逻辑耗时较长（超过 30 秒），需通过定时任务自动续期，防止业务未完成锁就过期了
   - 和本地锁一样，尽量不要在锁里做 IO 慢操作
4. **安全解锁**：使用 Lua 脚本校验 value 后删除，保证原子性
   ```lua
   if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1])
   else
       return 0
   end
   ```
   - **为什么要校验 value？** 防止误删其他实例的锁（例如锁超期自动释放了，别的实例拿到了锁，本方还在释放旧锁）
   - **为什么用 Lua？** 保证"查 → 判 → 删"三步是原子操作，避免并发时两步之间被插队。本质是保证单次网络请求，多次网络请求之间锁的状态可能已被其他客户端修改
   - **不用 Lua 的写法是错的**：先 GET 再 if DEL 不是原子的，并发下可能判断通过但删除时锁已是别人的

## 六、生产问题（缓存穿透 / 击穿 / 雪崩）

一个redis的使用，根据需求设置redis，选择更新策略、删除策略。这里的生产问题就是几个比较典型的redis使用场景。

<br />

贯穿始终的宗旨：不要让请求打满mysql，把mysql打爆炸了， redis 除了 提高qps，还有就是保护下游数据库的作用

### 6.1 缓存穿透

**定义**：大量请求查询**缓存和数据库中都不存在**的数据，每次请求都直接打到 MySQL，导致 DB 压力极大。

**核心特征**：不是"单个不存在的数据"，而是**缓存和 DB 里都没有**，大量请求穿透了缓存层直达 DB。可以是请求一个key，也可以是多个key，核心是null。

**解决方案对比**

| 方案        | 做法                                             | 适合场景             | 优点                                      | 缺点                                |
| --------- | ---------------------------------------------- | ---------------- | --------------------------------------- | --------------------------------- |
| **空值缓存**  | 查不到数据时，在 Redis 里存一个空 key（TTL 设短，如 1\~3 分钟）     | 合法 key 数量少、数据量小  | 实现简单，零误判                                | 数据量大时 Redis 内存占用高（恶意攻击可塞满大量空 key） |
| **布隆过滤器** | 启动时把所有合法 key 预加载到位数组中，请求来了先判断 key 是否合法，不合法直接拦截 | 合法 key 数量大（百万级+） | 内存占用极少（1000 万 key 约 10MB），从入口拦截不走 Redis | 实现复杂，有极低误判率，需要维护数据同步              |

**为什么数据量大的时候必须用布隆过滤器？**

```
恶意攻击遍历 1 亿个不存在的 ID
→ 空值缓存方案：Redis 里存 1 亿个空 key → 内存爆了
→ 布隆过滤器：1 亿个 key 也只要约 100MB 固定内存 → 完全扛得住
```

布隆过滤器存的是"key 是否存在的指纹"，不是 key 本身，内存占用和数据量不成正比增长。

### 6.2 缓存击穿

**定义**：一个**热点 key 刚好过期**的瞬间，大量并发请求同时打到数据库，导致 DB 压力暴增。只需要更新一个缓存。

**核心特征**：数据本身是存在的（缓存里有，只是刚好过期），问题出在**过期的那一瞬间**的高并发。

**解决方案**

| 方案                      | 做法                                       | 优点                | 缺点             |
| ----------------------- | ---------------------------------------- | ----------------- | -------------- |
| **分布式锁 + Double Check** | 只让一个请求拿锁去查 DB 重建缓存，其他请求等锁，锁内二次检查缓存是否已被重建 | 避免大量请求同时打 DB，实现简单 | 加锁有额外开销，锁超期需续期 |
| **热点 key 永不过期**         | 不设置 TTL，由后台定时任务主动更新缓存                    | 完全避免过期瞬间的并发问题     | 需要额外维护后台更新逻辑   |

### 6.3 缓存雪崩

**定义**：**大量 key 在同一时间集中过期**，导致大量请求同时打到数据库，DB 压力暴增。需要更新所有缓存。

**核心特征**：不是单个 key 的问题，而是**大规模 key 同时过期**，导致整体缓存失效。

**解决方案**

| 方案              | 做法                                    | 优点            | 缺点              |
| --------------- | ------------------------------------- | ------------- | --------------- |
| **TTL 加随机抖动**   | 设置过期时间时，在基础 TTL 上加减一个随机值（如 ±5 分钟）     | 有效分散过期时间，简单高效 | 不能完全避免，只能降低概率   |
| **多级缓存**        | 本地缓存（如 LRU）+ Redis 双层缓存，Redis 挂了本地还能扛 | 容灾能力强         | 实现复杂，本地缓存一致性难保证 |
| **缓存预热 + 分散加载** | 系统启动时逐步加载缓存，错开过期时间                    | 避免启动瞬间雪崩      | 需要额外初始化逻辑       |

### 6.4 对比总结

| 问题     | 核心原因        | 发生时机                 | 影响范围          | 核心解决方案          |
| ------ | ----------- | -------------------- | ------------- | --------------- |
| **穿透** | 数据 DB 里也不存在 | 持续发生（只要有人攻击/请求不存在数据） | 单个或少量不存在的 key | 空值缓存 / 布隆过滤器    |
| **击穿** | 热点 key 刚好过期 | 过期的那一瞬间              | 单个热点 key      | 分布式锁 / 永不过期     |
| **雪崩** | 大量 key 同时过期 | 集中过期的时间点             | 大规模 key       | TTL 随机抖动 / 多级缓存 |

## 七、过期删除与内存淘汰

前提：我们的需求就是，在cpu消耗不高的前提下，保证内存高效使用，在实践的时候有 热门和冷门key需要处理。

Redis 过期删除和内存淘汰最本质的区别：一个是业务驱动的主动清理，一个是内存兜底的强制保护，二者分层配合，共同保障 Redis 的内存高效使用。

### 7.1 过期删除策略

**前置知识**：key的过期时间如何存储？用一个expires字典存储（O(1)）。client请求到来，去字典中查找，判断exp是否过期，没有过期就找value返回。

**核心问题**：什么时候删除过期的key？两个方向：

- 下一次访问的时候包含检查，顺手删除
- 定时扫描字典，检查，删除过期key

**删除时机本质**：在省CPU和省内存之间做取舍。

- 顺手删除 → 利好CPU，内存占用高
- 定时扫描 → 利好内存，CPU占用高

**三种删除过期策略，redis默认开启**

| 策略     | CPU 占用 | 内存占用 | Redis 是否启用   |
| ------ | ------ | ---- | ------------ |
| 惰性删除   | 低      | 高    | ✅ 默认         |
| 定期随机删除 | 中      | 中    | ✅ 默认         |
| 定时扫描删除 | 高      | 低    | ❌ 无此方案，仅用于对比 |

**策略协作方式**

惰性删除和定期删除策略是redis默认就开启的，我们无法修改，只能调整定期删除的随机参数。

- **惰性删除**：依托访问动作清理热点过期键
- **定期扫描**：主动抽检回收冷门过期键

二者互补完成过期数据清理。

### 7.2 内存淘汰策略LRU LFU

删除策略仅能解决无效内存占用，无法解决数据堆积带来的内存超限问题。内存淘汰策略就是在内存占用超过阈值时执行。

**两类策略**

- **不淘汰数据**：内存达到上限后直接拦截新增写入操作，原有数据完整保留。数据安全性最高，但无法再存入新缓存
- **淘汰数据**：内存触顶时主动清理低频冷门键，优先留存高频热点数据。能持续写入新数据，缓存资源利用率更高

**按范围分类**

| 策略           | 范围           | 算法  | 说明             |
| ------------ | ------------ | --- | -------------- |
| allkeys-lru  | 全库所有 key     | LRU | 全体键里删最久不用的     |
| allkeys-lfu  | 全库所有 key     | LFU | 全体键里删使用频次最低的   |
| volatile-lru | 仅设置过期时间的 key | LRU | 只在过期键里删最久不用的   |
| volatile-lfu | 仅设置过期时间的 key | LFU | 只在过期键里删使用频次最低的 |

**LRU vs LFU**：LRU是最近最少使用（recently），LFU是使用频次最低（frequently）。

**业务场景选择**

先确认有没有"永久有效的基础配置缓存"（如系统配置、全局黑名单）：

| 场景                       | 选型                    | 原因                           |
| ------------------------ | --------------------- | ---------------------------- |
| **有永久 key**（如系统配置）       | 只能用 volatile 系列       | allkeys 会删掉永久 key，导致配置丢失     |
| **全临时数据**（所有 key 都设 TTL） | allkeys 或 volatile 均可 | allkeys 腾空间更大，推荐 allkeys-lru |

再根据数据访问特征选算法：

| 特征                       | 选型     | 典型场景         |
| ------------------------ | ------ | ------------ |
| 热点数据访问稳定（某几个 key 持续高频）   | LFU    | 热门商品、大 V 主页  |
| 热点随时间迁移（现在火的 vs 下一波火的不同） | LRU    | 新闻资讯、实时榜单    |
| 周期性访问（工作日上班 vs 下班休息）     | LFU 更好 | 长期数据积累后频次更准确 |

**常用推荐**：

- 无永久 key → `allkeys-lru`（通用稳妥）
- 有永久 key → `volatile-lfu`（频次赛马，保留常客）

**总结**

- 底层过期清理是固定不变的地基
- 业务缓存设计、内存淘汰配置是上层建筑，必须依托地基来规划

## 八、缓存使用整体框架

一套合格的 Redis 缓存策略，依次考量以下环节：

### 8.1 核心五环节

1. **数据结构选取**
   根据业务形态选String/Hash/Set/ZSet/List，匹配存取、排序、去重、对象存储需求，是缓存效率与功能的基础。
2. **TTL过期时间，key string 设置**
   管控缓存生命周期，自动清理失效、低频冷数据；规避内存溢出，同时弱化缓存与数据库数据不一致的问题。
3. **缓存读写策略**
   主流旁路缓存、读写穿透、写回模式，规范缓存和数据库的读写先后、更新逻辑，核心解决**数据一致性**问题。
4. **持久化方案**
   RDB、AOF按需配置，应对服务宕机、重启数据丢失风险；临时高频变动数据可关闭持久化，核心业务数据开启兜底保存。
5. **并发锁与并发问题**
   处理高并发争抢更新、缓存击穿/穿透/雪崩；用到Redis分布式锁、WATCH乐观锁、事务、Lua脚本保证并发安全。

### 8.2 配套关注点

- **内存淘汰策略**：内存占满后的数据清理规则，和TTL过期搭配，防止Redis内存打爆
- **缓存异常防护**：围绕并发衍生的三大经典问题：穿透、击穿、雪崩，结合过期、锁、布隆过滤器共同解决

## 九、持久化方案（RDB vs AOF）

| 维度 | RDB（快照） | AOF（追加日志） |
| --- | --- | --- |
| **原理** | 定时生成全量快照（dump.rdb） | 追加记录每个写命令（appendonly.aof） |
| **数据完整性** | 可能丢最后一次快照后的数据 | 可配 everysec（丢1秒）或 always（不丢） |
| **恢复速度** | **快**（直接加载文件到内存） | 慢（逐条回放命令） |
| **文件体积** | 小（二进制压缩） | 大（文本协议，存的是命令） |
| **对性能影响** | 写时复制（fork 子进程），父进程几乎不阻塞 | 写频率高时可能影响 QPS |
| **适用场景** | 允许分钟级数据丢失、重启恢复要快 | 数据安全性要求高、能接受重放耗时 |

**常用建议**：两者都开（Redis 默认配置），RDB 用于快速恢复，AOF 用于保证数据不丢。Redis 4.0+ 支持混合持久化（AOF 重写时生成 RDB 格式头，兼顾速度和体积）。

# 1.redis为什么快？
前提，这里的快，就是指 一系列增删改查操作，执行的速度。
redis快的原因是，  内存， 单线程  配合单线程的 io多路复用
1. redis存在在内存中，数据读取很快，没有文件io开销。
2. 单线程，没有线程切换开销
3. IO 多路复用让单线程能同时监听多个连接， 避免被单个连接阻塞 ，从而能 快速响应其他客户端的请求（这个请求就是别人已经发过来的增删改查的操作嘛）
4. 补充：底层数据结构极其高效    

# 2.redis 几大存储数据结构区别？
区别，主要就看两点： 一个是 存的数据到底是什么   一个是 这个结构可以执行什么 数据操作
一个数据具体选择哪个数据结构呢？  分析这个数据是什么，以及我们需要对数据执行什么操作
redis 存储本质都是字符串（底层 SDS）

| 结构 | 存储内容 | 核心操作 | 典型场景 | 注意事项 |
| :--- | :--- | :--- | :--- | :--- |
| **String** | 字符串/数字/二进制 | `SET/GET` (基础读写)<br>`INCR/DECR` (**原子自增**，无需加锁) | 缓存、计数器、分布式锁 | 避免大 Key（>10KB） |
| **List** | 有序字符串列表（可重复） | `LPUSH/RPOP` (**两端操作**，实现队列/栈)<br>`LRANGE` (范围查询) | 消息队列、朋友圈时间线 | 非阻塞用 List，阻塞队列用 `BLPOP` |
| **Set** | 无序字符串集合（唯一） | `SADD/SREM` (增删元素)<br>`SINTER/SUNION` (**集合运算**，一行命令搞定交集/并集) | 标签、共同好友、抽奖 | 内存随元素增多，注意去重开销 |
| **ZSet** | 有序集合（带 Score 分数） | `ZADD` (带分数添加)<br>`ZRANGE` (**按排名查询**)<br>`ZINCRBY` (**原子增加分数**) | 排行榜、延迟队列 | Score 可重复，Member 唯一 |
| **Hash** | Field-Value 键值对 | `HSET/HGET` (**字段级读写**，不用拉取整个对象)<br>`HINCRBY` (字段原子自增) | 对象缓存、购物车 | go-redis 支持自动序列化 struct |
| **Bitmaps** | 位数组（0/1） | `SETBIT/GETBIT` (**位级操作**)<br>`BITCOUNT` (**统计 1 的个数**，极快) | 签到、活跃用户统计 | 极致省内存，1 年签到仅 46 字节 |
补充：
原子性操作 ：单线程模型保证命令执行不被打断。各数据结构提供 无需加锁、天然线程安全 的专属操作，高并发下性能极高。

# 3.ttl设置多少？ 业务影响这里的参数， 参数定大小，反向牵动业务运行
这个问题就看起来比较简单，但是还是 具体梳理：
ttl设置多少会影响什么？ 内存、性能与数据一致性。
也不太头脑风暴，一句话 需要长，但别太长，  需要短，但别太短。

TTL 拉太长，堆内存、脏数据久，倒逼内存淘汰频繁启动；
TTL 缩太短，丢命中率、炸数据库，过期删除 CPU 压力暴涨；
取值贴合业务更新频率，就能平衡内存、性能与数据一致性。

核心问题：为什么ttl时间要贴合 业务更新频率？
- 因为缓存的目的是 提高访问速度，减少数据库压力 同时需要保持数据一致性。
只谈论数据库压力，肯定是ttl越长越好，但是这里带来的一个问题就是，数据一致性没有保障，
可以说，ttl 短，就是为了 数据一致性。   越短，refresh频次越高，数据越fresh
两个一致性情况：   主要靠业务主动更新保障，缓存过期只是兜底手段。
一个是 缓存过期，引起的 mysql            mysql开销，
一个是 mysql数据更新，引起的   缓存更新   缓存更新开销，
两个开销不一样，但是目的都是为了数据一致性，

在这个环节中，ttl的作用就是 缓存过期的兜底手段，所以说不需要太过于纠结 ttl到底要详细到多少，根据更新评率去适合就可以了，   因为考虑兜底，所以假设这里一致性 只依赖 兜底， 那么 db1分钟更新一次，那么ttl就设置为1分钟就可以了。


方法结论导向：还是优先贴合业务需求，然后再精细化考虑性能问题。一致性问题 
- 秒杀、临时活动、验证码：秒 / 分钟级 TTL（几十秒～30 分钟），短期用完立刻失效
- 商品、资讯、首页通用缓存：1~6 小时，兼顾新鲜度与访问命中率
- 用户基础资料、固定配置：半天～1 天，改动频率低，不用频繁过期重建

# 4. 数据一致性问题


因为引入了redis，那么数据更新时，一个问题，先更新缓存，还是更新数据库？

理论上两个方案：
先更新数据库再处理缓存，是主流稳妥做法，契合版本号方案，能有效减少数据错乱问题。 但是有 不一致窗口问题
先更新缓存再改动数据库，极易产生脏数据，业务开发中一般不会选用。

结论：先更新数据库，再更新缓存。-- cache aside方案  决定好 更新的顺序  

cache aside 方案：
先更新 数据库，  然后直接删除缓存， 等 下一次请求再新建缓存

接下来主要剖析，怎么新建缓存？  永远要追求原子性操作方案

主要靠业务主动更新保障，缓存过期只是兜底手段。

直接生成新 kv，覆盖旧kv，    旧kv怎么淘汰呢？ 依赖 定时缓存+内存淘汰 删除

版本号方案更新缓存的优点？？？

# 5. 用redis 实现分布式锁
sync是内存级别的锁，不能跨服务器使用， redis是分布式锁，可以跨服务器使用。

加上 Double Check（重试机制）后的极简核心步骤：

1. **尝试加锁**：执行 `SET key value NX PX 30000`
2. **Double Check**：若加锁失败，**循环重试**（自旋等待），直到成功或超时。
3. **执行业务**
4. **安全解锁**：Lua 脚本校验 value 后删除。


# 7.过期删除和内存管理？ why how？  业务说了算，按需挑选规则
前提：我们的需求就是，在cpu消耗不高的前提下，保证内存高效使用，在实践的时候有 热门和冷门key需要处理 

Redis 过期删除和内存淘汰最本质的区别：一个是业务驱动的主动清理，一个是内存兜底的强制保护，二者分层配合，共同保障 Redis 的内存高效使用。

前置知识：  key的过期时间如何存储 判断过期流程？ 
用一个expires 字典存储（o1）   
client请求到来，然后去字典中查找，然后判断exp是否过期，没有过期就去找value，返回

核心问题：  什么时候删除过期的key？ 两个方向，下一次访问的时候包含检查，顺手删除    ，  定时扫描字典，检查，删除过期key
前置知识梳理： 什么时候删除 key  ， 核心切入点：删除时机本质就是在省 CPU和省内存之间做取舍
顺手，利好cpu，但是内存占用会增加。
定时扫描，利好内存，但是cpu占用会增加。
三个删除策略：
1. 惰性删除  cpu占用低，内存占用高
2. 定期随机删除  cpu占用中，内存占用中
3. 定时扫描删除  cpu占用高，内存占用低  ，redis压根没这个方案，只是我们用来对比，为什么redis 默认使用的前两者

辅助理解问题： 策略是怎么协作的？  
前提：我们的需求就是，在cpu消耗不高的前提下，保证内存高效使用，在实践的时候有 热门和冷门key需要处理 
核心：
- 底层过期清理是固定不变的地基；
- 业务缓存设计、内存淘汰配置是上层建筑，必须依托地基来规划。
惰性删除和定期删除策略是 redis默认就开启的，而且我们无法修改，我们只能顶多只能 调整 定期删除的 随机参数。
协作讲解：惰性删除依托访问动作清理热点过期键，定期扫描主动抽检回收冷门过期键，二者互补完成过期数据清理。

接下来就进入到内存淘汰策略了。
内存占用分为有效内存占用和无效内存占用，删除策略仅能解决无效内存占用，能提高内存有效率无法解决数据堆积带来的内存超限问题
内存淘汰策略，就是为了解决这个问题的。   从而保证redis的高效运行。
辅助问题：  什么时候执行策略？ 当内存占用超过阈值时，就会执行内存淘汰策略。

有两类策略，一类是不淘汰数据，一类是淘汰数据。
不淘汰数据：死守现有全部缓存，不丢存量数据，但无法新增内容 
内存达到上限后，直接拦截新增写入操作，原有数据完整保留不变；查询、删除已有键的操作均可正常执行，数据安全性最高。缺点是无法再存入新缓存，业务新增数据的需求会被限制。

淘汰数据：舍弃低使用率缓存，保全核心常用数据，支持持续写入新数据，缓存资源利用率更高
内存触顶时主动清理低频冷门键，优先留存高频热点数据；在基本不影响常规缓存使用的前提下释放内存，能够持续写入新数据，保障 Redis 正常读写流转，缓存资源利用率更高。

这里还有两个分类：全库所有 Key   仅设置过过期时间的 Key
前者：最大限度腾出内存空间
后者：腾出内存空间的同时，保障了 未过期的重要缓存，即使频率低

allkeys-lru：全体键里删最久不用的
allkeys-lfu：全体键里删使用频次最低的

volatile-lru：只在过期键里删最久不用的
volatile-lfu：只在过期键里删使用频次最低的

核心问题：lru跟lfu的区别？ recently  frequently

根据业务场景，选择淘汰策略
常见场景：有基础配置的类的缓存，永久有效，那么肯定只能 volatile，然后再选择是频次还是时间

缓存是否 具备 有基础永久缓存，  然后再看 业务实现是什么结果，频次就lfu，时间就lru。
大多数情况下 都是 volatile-lfu的策略。
总结：
核心：
- 底层过期清理是固定不变的地基；
- 业务缓存设计、内存淘汰配置是上层建筑，必须依托地基来规划。

# 缓存使用流程？
**总结得非常完整，这五块刚好构成一套闭环的Redis缓存设计策略**，覆盖从选型使用、数据生命周期、数据同步、宕机兜底、并发安全全流程，业务开发和面试设计题都会围绕这些点展开。

### 逐项核对定位
1. **数据结构选取**
根据业务形态选String/Hash/Set/ZSet/List，匹配存取、排序、去重、对象存储需求，是缓存效率与功能的基础。

2. **TTL过期时间设置**
管控缓存生命周期，自动清理失效、低频冷数据；规避内存溢出，同时弱化缓存与数据库数据不一致的问题。

3. **缓存读写策略**
主流旁路缓存、读写穿透、写回模式，规范缓存和数据库的读写先后、更新逻辑，核心解决**数据一致性**问题。

4. **持久化方案**
RDB、AOF按需配置，应对服务宕机、重启数据丢失风险；临时高频变动数据可关闭持久化，核心业务数据开启兜底保存。

5. **并发锁与并发问题**
处理高并发争抢更新、缓存击穿/穿透/雪崩；用到Redis分布式锁、WATCH乐观锁、事务、Lua脚本保证并发安全。

---

### 补充2个配套必关注小点，策略更严谨
1. **内存淘汰策略**
内存占满后的数据清理规则，和TTL过期搭配，防止Redis内存打爆。
2. **缓存异常防护**
围绕并发衍生的三大经典问题：穿透、击穿、雪崩，结合过期、锁、布隆过滤器共同解决。

# Eino 框架里 Tools / MCP / Skills 三者 区别 + 共同点（面试原版，精准好背）
基于 CloudWeGo Eino 官方定义，只讲**面试能用、工程真实含义**，不搞玄学。

## 一、先各自一句话定义
1. **Tool（工具）**
原子最小单元，**单一能力**，只干一件事，比如调一个接口、查数据库、发 HTTP 请求。

2. **MCP（Model Context Protocol 模型上下文协议）**
不是能力，是**统一规范/通信协议**；
统一所有 Tool、Skill 的**入参、出参、调用格式、上下文结构、错误格式**，让大模型能统一理解、调度工具。

3. **Skill（技能）**
业务上层封装，**把多个 Tool + 编排逻辑（分支/顺序/判断）组合成一个完整业务能力**。

---

## 二、三者共同点
1. 都是为了**给 AI Agent 扩展能力**，让大模型不只是聊天，能执行外部业务动作。
2. 全部**遵循 MCP 协议规范**做入参出参定义。
3. 都可以被 Agent 框架**统一发现、调度、调用**。
4. 都属于 Agent 的「手脚」能力层，不属于 LLM 大脑。

---

## 三、核心差异（最关键）
### 1. 层级不同
- **Tool：最底层** → 原子能力
- **MCP：中间规范层** → 统一标准
- **Skill：上层业务层** → 组合封装能力

### 2. 粒度不同
- Tool：粒度最小，**单一职责**
- Skill：粒度粗，**业务完整流程**
- MCP：无业务粒度，只是**格式协议**

### 3. 是否可编排
- Tool：**不能内部编排**，只能独立执行单一功能
- Skill：**可以内部编排**，串行/并行/条件分支调用多个 Tool
- MCP：只管格式，不管业务逻辑编排

### 4. 作用定位
- Tool：干活的**最小执行者**
- MCP：统一语言的**规则标准**（统一大模型与工具的对话格式）
- Skill：面向业务的**封装技能**，对外暴露一个业务能力

---

## 四、直观例子（一秒懂）
假设做一个「出行规划」Agent：
- **Tool**
  查天气Tool、查火车票Tool、查酒店Tool —— 每个只干一件事。

- **Skill**
  「出行规划Skill」
  内部自动：先查天气 → 再查车票 → 再推荐酒店，**把多个 Tool 编排成一套流程**。

- **MCP**
  规定好：所有 Tool / Skill 入参怎么传、返回什么字段、上下文怎么带、错误码怎么定，大模型按这套统一格式调用，不用适配每个工具不同格式。

---

## 五、极简对比表（背这个就行）
| 维度 | Tool | MCP | Skill |
|------|------|-----|-------|
| 定位 | 原子工具、最小执行单元 | 模型上下文通信协议、统一规范 | 业务技能、工具组合编排 |
| 粒度 | 细、单一功能 | 无业务粒度 | 粗、完整业务流程 |
| 可否编排 | 不可，只能单功能 | 不负责编排 | 可内部编排多Tool |
| 依赖 | 遵循 MCP 协议 | 统一约束 Tool/Skill | 由多个 Tool 组成，遵循 MCP |
| 举例 | 查天气、HTTP请求、DB查询 | 统一入参出参、上下文格式 | 出行规划、工作流审批 |

---

## 六、面试标准回答话术（直接背）
> 三者共同点是都属于 AI Agent 的能力扩展层，用来给大模型赋予外部执行能力，并且全部遵循 MCP 协议做统一入参出参和上下文规范，能被 Agent 统一调度。
>
> 区别在于层级和粒度：
> Tool 是最底层的原子能力，只负责单一职责，是最小执行单元；
> MCP 是中间的统一通信协议，用来规范所有工具和技能的调用格式、上下文结构，解决大模型调度多工具格式不统一的问题；
> Skill 是上层业务封装，内部可以编排多个 Tool，加上业务流程和分支逻辑，封装成一个完整的业务技能对外提供服务。

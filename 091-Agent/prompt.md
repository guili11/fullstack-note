## 核心原则

- **聚焦 Node 本身**：节点职责单一，prompt 聚焦节点逻辑。 ✅
- **Context 注入**：明确节点需要哪些数据，减少无关信息，提高 token 使用效率。 ✅
- **JSON 输出规范**：通过格式约束、QA 示例、规则保证输出结构化，减少幻觉。 ✅
- **关注 Node Graph 流程**：节点之间的输入输出要配合，保证整个 workflow 的连贯性。 ✅

**核心目标**：减少幻觉、减少 token 消耗、规范化输出。

---

## 补充的几个点

### 1. 节点内部"状态"管理
- 除了输入输出，有些节点可能需要记录临时状态或历史信息
- 例如 n2 生成的能力点，是否保留历史版本便于调试或增量更新？
- 这会影响 workflow 的稳定性和复用性

### 2. 错误和异常处理
- prompt 设计时是否考虑"节点处理失败怎么办"
- 例如输入文本空、JSON 输出不完整、LLM 幻觉出现
- 这是 workflow 健壮性的一部分

### 3. 能力点/信息抽象层次
- 你提到 context 注入，但有时节点处理的数据是否需要先抽象成"能力点、技能标签、结构化字段"，再传给下一个节点？
- 抽象层次决定 token 使用效率和匹配准确性

### 4. 节点之间的数据依赖显式化
- Node Graph 里不仅要考虑顺序，也要考虑哪些数据是必须的、哪些是可选的
- 可以用"数据 contract"形式明确每个节点需要的字段和类型

### 5. prompt 可扩展性
- 当 workflow 增加节点或改变顺序时，如何保证 prompt 不需要每次大幅修改
- 例如模板化 prompt + 可配置上下文字段

## 关键要点

**通过调整 prompt 减少 LLM 思考时间**

**max token 限制**

**prompt 模版**：使用模版管理 prompt 不是为了方便 AI，是为了增强 prompt 的可扩展性

## Prompt 结构组成

### 1. 身份提示（Identity）
- **内容**：告诉模型"你是谁/角色是什么"
- **作用**：约束模型风格、职责、理解角度

### 2. 任务给与（Task）
- **内容**：明确模型需要做什么，节点逻辑、分析目标、输出目的

### 3. 信息给与（Context / Input）
- **内容**：注入节点需要的数据、简历文本、能力点、岗位要求等
- **作用**：控制上下文范围 → 降低 token 消耗

### 4. JSON 格式返回要求（Output Format）
- **内容**：明确字段名、类型、嵌套结构
- **方法**：用 QA 样例或约束规则强化

### 5. 约束（Constraints）
- **内容**：max token、输出长度、格式强制约束、值域限制
- **作用**：降低幻觉、保证规范化输出

---

## Token 限制与节点依赖

### max token 限制
→ 每次 LLM 调用输入 + 输出总长度受限

### 节点依赖
→ 后续节点依赖前置节点的输出（如能力点列表、质量分析）

### 风险
- 前置节点输出被截断 → 下游节点得到不完整信息
- token 截断导致 JSON 不完整 → 下游解析失败
- 结果不准确 → 匹配分析 / 建议反馈失真

### 核心矛盾
**token 限制 vs 保证信息完整性**

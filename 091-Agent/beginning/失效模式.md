4. 工程上最常用的 4 类失效模式（你可以先用这个）
① 信息失效（knowledge failure）
信息不在模型里 / 或不可靠

表现：

编造事实
outdated
不知道最新状态

👉 常见修复：RAG / tool

② 结构失效（structural failure）
任务结构没被正确表达/理解

表现：

答案乱
没步骤
API/设计不一致

👉 修复：prompt结构化 / schema / few-shot

③ 状态失效（state failure）
多步过程中信息丢失或漂移

状态失效的本质是“隐式状态 + 无结构存储”，上下文限制只是加速状态丢失的因素

表现：

前后矛盾
agent跑偏
长任务崩

维护状态
👉 修复：workflow / memory / state machine

通过把“隐式状态”显式化并外置存储，使每一步调用都能恢复必要上下文，从而降低状态漂移
每一步都重新构造context（state injection）
减少“隐式状态依赖”，转为“显式状态控制”


④ 决策失效（decision failure）
模型没有稳定选择策略

表现：

同问题不同答案
策略不收敛
建议随机

👉 修复：rule / constraint / planning


总结发现问题有挺多种的，但是最终的落地工具还是 prompt

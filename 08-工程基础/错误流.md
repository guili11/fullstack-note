# 错误流处理（Error Flow Handling · 实战版）

核心三问：

- handler 有没有写业务逻辑？
- service 有没有直接操作 DB 细节？
- repo 有没有掺杂业务判断？

***

## 一、整体流程（先建立脑图）

```text
repo：
    - 返回技术错误（必须 wrapping）

↓

service：
    - 判断错误类型（关键决策点）
        ├─ 可预期业务场景 → 转换为业务错误
        ├─ 可透出的技术语义 → 保留 / 轻包装
        └─ 不可预期系统错误 → 统一兜底（internal error）

↓

handler：
    - 只做协议映射（HTTP）
    - 不理解业务细节

↓
response + logging
```

👉 你写代码时，本质就是在维护这条链路

***

# 二、各层“具体怎么写”（核心）

***

## 1️⃣ Repo 层（错误产生 + wrapping）

### 规则

```text
- 只返回技术错误
- 必须加上下文（wrapping）  --方便日志记录错误来源
- 不允许定义业务错误
```

***

### 标准写法

```go
func GetUser(id string) (*User, error) {
    var user User

    err := db.First(&user, "id = ?", id).Error
    if err != nil {
        return nil, fmt.Errorf("repo.GetUser: %w", err)
    }

    return &user, nil
}
```

***

## 2️⃣ Service 层（语义定义 + 透传）

### 规则

```text
- 透传技术错误（不处理）
- 定义业务错误（ErrXXX）
- 不打日志
- 不关心 HTTP
```

***

### 标准写法

```go
func GetUser(id string) (*User, error) {
    user, err := repo.GetUser(id)
    if err != nil {
        return nil, err // ✅ 直接透传
    }

    if user != nil {
        return nil, ErrUserAlreadyExist // ✅ 定义业务语义
    }

    return user, nil
}
```

***

## 3️⃣ Handler 层（映射 + 最终处理）

基于 Gin：

***

### 核心规则

```text
- 必须处理所有 error（不能继续往下）
- 使用 errors.Is 将错误映射为HTTP结果
- 业务错误 → 返回 4xx
- 系统错误 → log + 返回 500
```

***

### 标准写法（模板级）

```go
user, err := service.GetUser(id)

if err != nil {

    // 1️⃣ 业务错误
    if errors.Is(err, ErrUserNotFound) {
        c.JSON(404, gin.H{
            "code": "USER_NOT_FOUND",
            "message": "user not found",
        })
        return
    }

    // 2️⃣ 系统错误
    log.Errorf("GetUser failed: %v", err)

    c.JSON(500, gin.H{
        "code": "INTERNAL_ERROR",
        "message": "internal server error",
    })
    return
}

c.JSON(200, user)
```

***

# 三、错误处理“操作步骤”（你写代码时照着做）

```text
1. repo 写数据操作 + wrapping error
2. service 调用 repo
   - 有 error → 直接 return
   - 无数据 → 返回业务错误
3. handler 调用 service
   - if err != nil：
       - 判断业务错误（errors.Is）
       - 否则 → 系统错误
4. 返回 JSON + 必要日志
```

***

# 四、错误分类标准（非常实用）

```text
业务错误（可预期）：
- user not found
- password incorrect
- permission denied

系统错误（不可控）：
- 数据库错误
- 网络错误
- panic
```

# 五、和控制流设计的结合（关键点）

你前面学的：

- Guard Clause
- Fail Fast

在错误流中就是：

```go
if err != nil {
    return // 每一层都必须这样
}
```

👉 本质：

> **错误不能“继续往下走”**

# 六、一个完整示例（强烈建议你看一遍）

***

## repo

```go
func GetUser(id string) (*User, error) {
    var user User
    err := db.First(&user, "id = ?", id).Error
    if err != nil {
        return nil, fmt.Errorf("repo.GetUser: %w", err)
    }
    return &user, nil
}
```

***

## service

```go
func GetUser(id string) (*User, error) {
    user, err := repo.GetUser(id)
    if err != nil {
        return nil, err
    }

    if user.ID == 0 {
        return nil, ErrUserNotFound
    }

    return user, nil
}
```

***

## handler

```go
func GetUserHandler(c *gin.Context) {
    id := c.Param("id")

    if id == "" {
        c.JSON(400, gin.H{"message": "invalid id"})
        return
    }

    user, err := service.GetUser(id)

    if err != nil {
        if errors.Is(err, ErrUserNotFound) {
            c.JSON(404, gin.H{"message": "user not found"})
            return
        }

        log.Errorf("GetUser failed: %v", err)

        c.JSON(500, gin.H{"message": "internal error"})
        return
    }

    c.JSON(200, user)
}
```

# 八、一句话版本（你以后复习用）

```text
错误从 repo 产生，service 定义语义，handler 统一处理并对外响应
```

***

如果你下一步继续优化，我建议你直接升级这一层：

👉 **把 handler 里的 error 处理抽成 middleware（统一错误出口）**

这样你这套模型就会从“规范”升级成“自动执行”。

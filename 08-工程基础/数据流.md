# 1.数据流的一个关键问题：

> 数据在不同层之间流动时，必须“变形”，而不是“透传”

DB(Model) → Service(Decode + 业务加工) → Controller(DTO输出)

JSON 泄漏
nil / 空指针
字段不一致
controller 乱补数据

# 2.接口的完整数据流（标准版）

```
[请求]
   ↓
Controller（只拿参数）
   ↓
Service（核心数据流控制）
   ↓
Repo（查 DB）
   ↓
DB（JSON）
   ↑
Repo 返回 model.Word
   ↑
Service 做映射（JSON → struct）
   ↑
Service 返回 domain.WordSearchResponse
   ↑
Controller 直接返回 JSON
```

repo utils,二者同为底层基础，但是repo由于接触数据库，返回值只能是model，需要在service中做数据映射。

utils不一样，数据来源一般是做请求啊，加密啊，在utils中就可以 准备好为 service中需要的 domain了。

service，关键职责在数据流中就是，准备好response。

controller，在数据流中，只关注根据err，是否返回res，不在乎res是什么，怎么准备好response

# 三、关键点：数据在“哪里变形”

&#x20;

你要重点盯这 3 个点：

***

## 1️⃣ 入参：HTTP → domain

```
word := c.Query("word")
```

👉 这里是：

```
string → 业务语义
```

简单，可以忽略

***

## 2️⃣ 查库：model → domain（核心！！！）

你现在的问题就在这里。

```
model.Word{
    Definitions: JSON
}
```

👉 必须变成：

```
[]Definition
```

***

## 3️⃣ AI：外部数据 → domain

```
utils.SearchWord()
```

👉 本质是：

```
不可信数据 → 标准结构
```

***

# 四、数据流的“控制权”在哪一层？

👉 只能在 **service 层**

这是原则，不是建议。

***

## 为什么？

### ❌ 如果在 controller 做：

- &#x20;每个接口都要写一遍转换&#x20;
- &#x20;逻辑分散&#x20;
- &#x20;极易不一致&#x20;

***

### ❌ 如果在 repo 做：

- &#x20;repo 不应该知道业务结构&#x20;
- &#x20;会污染数据层&#x20;

***

### ✅ 只能在 service：

- &#x20;有业务语义&#x20;
- &#x20;有完整上下文&#x20;
- &#x20;可以做 fallback（DB → AI）&#x20;

***

# 五、你现在应该建立的“数据流规范”

我给你一套可以直接写进你项目文档的：

***

## ✅ 1. 分层数据类型

```
// DB 层
model.Word

// 业务层
domain.WordSearchResponse

// 外部（AI）
utils 返回 domain（或专门 AI DTO）
```

***

## ✅ 2. 映射函数必须存在

```
model → domain
domain → model（可选）
```

👉 不能 inline 写在逻辑里

***

## ✅ 3. controller 不允许构造数据

```
❌ res := {}
❌ res.Word = xxx
```

👉 controller 只能：

```
c.JSON(200, res)
```

***

## ✅ 4. JSON 不能出现在 service 以上

```
datatypes.JSON ❌
```

👉 一旦出现在 controller：

说明你架构已经坏了

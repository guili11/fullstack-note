# 前端开发路径（API-first / 偏服务端版）

---

## 0️⃣ 页面行为设计（必须前置）

> ⚠️ 不写 UI，而是定义“页面要做什么”

明确每个页面的：

- 功能
- 用户行为（点击 / 输入 / 触发）
- 对应接口

示例：

| 页面 | 行为 | 接口 |
|------|------|------|
| login | 登录 | POST /login |
| search | 查询单词 | GET /words?q=xxx |
| notebook | 获取单词本 | GET /words/list |
| notebook | 删除单词 | DELETE /words/:id |

👉 这是整个项目的驱动核心（相当于“需求 + 接口契约”）

---

## 1️⃣ 初始化项目

- Vite 创建项目（React / Vue + TS）
- 安装依赖：
  - axios
  - router
  - store（pinia / zustand / redux）

- 目录结构：

```

/view
/controller
/service
/store
/request
/utils
/components

````

---

## 2️⃣ 路由搭建

- 配置基础路由：

  - /login
  - /register
  - /search
  - /notebook

- 确保：

  - 页面可以正常跳转
  - 路由结构清晰（避免混乱嵌套）


路由提供页面级上下文，明确接口的归属、调用时机和数据生命周期，从而约束 HTTP 的设计与使用，避免接口层无序扩散。
---

## 3️⃣ HTTP 接口设计（重点）

> ⭐ 核心训练点（偏后端能力）

设计内容：

- 请求方法（GET / POST / DELETE / PATCH）
- 请求参数（query / body / path）
- 响应结构（统一格式）

推荐统一响应格式：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
````

需要思考：

* 401（未授权）如何处理？
* 业务错误 vs 技术错误如何区分？
* 是否需要分页（page / pageSize）？
* 是否需要缓存（ETag / Cache-Control）？

---

## 4️⃣ request 层（HTTP 技术封装）

职责：**只处理 HTTP 技术细节**

* baseURL 配置
* token 自动注入（Authorization）
* 响应拦截：

  * 统一错误处理
  * 401 自动跳转登录 / 清理 token

❌ 禁止：

* 写业务逻辑
* 操作 UI

---

## 5️⃣ service 层（业务接口语义）

职责：**API → 业务动作映射**

> 不要碰 HTTP 状态码  只做：业务语义 + 数据保证

按模块划分：

* auth：

  * login
  * register

* word：

  * search
  * save
  * list
  * delete

规范：

✅ 应该做的
接口语义化
login / searchWord / saveWord（不是 get/post）
参数约束
类型定义
必要校验
返回值统一
只返回 data
保证结构稳定
轻量业务规则
判空
默认值
基本合法性

* 只返回 `data`
* 错误直接抛出（throw）
* 不处理 UI / 不操作状态

---

## 6️⃣ store 层（状态中心）
（本次项目不需要全局的store）  唯一全局就一个用户信息：用户信息只需要token就可以获取到，token还是在requset自动注入的

职责：**只存数据，不做决策**

定义：

* user / token
* wordList / total
* loading

规范：

* 只提供 set / update 方法
* 不写业务逻辑
* 不直接调用接口

---

## 7️⃣ controller 层（核心）

> ⭐ 控制流 / 错误流 / 数据流的集中体现

职责：

* 调用 service
* 控制业务流程
* 更新 store
* 处理错误

示例：

```ts
async function loginController() {
  try {
    const data = await login()
    setUser(data)
  } catch (err) {
    handleError(err)
  }
}
```



---

## 8️⃣ UI 层（延后实现）

> ⚠️ UI 只是“承接层”，不是核心

职责：

* 展示数据
* 触发 controller
* 不直接调用 service

示例：

```tsx
<button onClick={loginController}>登录</button>
```

---

## 9️⃣ 打通链路

逐页面验证完整流程：

```
view → controller → service → request → backend
                ↓
              store → view
```

确保：

* 每个页面独立跑通
* 数据流清晰
* 错误可控

---

## 🔟 收尾优化

* loading 状态处理
* 错误提示（toast / message）
* 组件拆分（提高复用）
* 基本交互优化

---

# ✅ 最终核心顺序（必须遵守）

```
页面行为
→ 项目结构
→ 路由
→ HTTP设计
→ request
→ service
→ store
→ controller
→ UI
→ 打通链路
→ 优化
```

---

# 🧠 方法论总结

* 本质：**API-first（接口驱动开发）**
* UI：不是起点，而是终点
* controller：是整个前端的“大脑”
* store：只是“数据库”，不做决策
* service：只是“接口语义层”

👉 目标：构建清晰的 **控制流 + 数据流 + 错误流**

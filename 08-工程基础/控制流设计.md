## 控制流设计（Control Flow Design）

### 一、核心定义

控制流设计的本质是：

> **通过约束代码的执行路径，让逻辑更简单、可读、可预测**

***

## 二、三层结构（重点）

```text
目标（Target）
↑
原则（Principles）
↑
手段（Techniques）
```

***

## 三、目标层（Target）

### ✅ Happy Path First（快乐路径优先）

**定义：**
主流程必须是**最直、最清晰的一条执行路径**

**表现：**

- 代码从上往下可以顺读
- 核心逻辑不被 if/else 包裹
- 一眼能看出“这个函数在干嘛”

```go
// 理想结构（Happy Path）
validate
process
return result
```

***

## 四、原则层（Principles）

这些是“约束你写代码的规则”

### 1️⃣ Fail Fast（早失败）

**定义：**
一旦出现错误或非法状态，立即中断执行

**作用：**

- 防止错误污染主流程
- 减少状态复杂度

***

### 2️⃣ Flatten（扁平化）

**定义：**
控制结构必须尽量减少嵌套层级

**作用：**

- 提高可读性
- 降低认知负担

***

### 3️⃣ Happy Path First（主流程优先）

**定义：**
最核心逻辑必须处于“最外层结构”

**作用：**

- 强化代码表达能力
- 主次分明

***

## 五、手段层（Techniques）

### ✅ Guard Clause（卫语句）

**定义：**
在函数前部对异常情况进行判断，并立即 return

***

### 标准写法：

```go
if err != nil {
    return err
}
```

***

## 六、三层之间的关系（核心理解）

### 1️⃣ 手段 → 原则

Guard Clause 实现：

- ✅ Fail Fast（提前 return）
- ✅ Flatten（减少嵌套）
- ✅ Happy Path First（清理干扰）

***

### 2️⃣ 原则 → 目标

当你满足：

- Fail Fast
- Flatten
- Happy Path First

👉 自然得到：

> ✅ 清晰的 Happy Path（目标达成）

***

## 七、完整执行模型（建议直接记）

```text
目标：
- 让主流程（Happy Path）清晰可见

原则：
- Fail Fast（错误立即返回）
- Flatten（减少嵌套）
- Happy Path First（主逻辑优先）

手段：
- 使用 Guard Clause 提前 return，清理异常路径

结果：
- 代码呈现线性结构（Happy Path）
```

***

## 八、对比示例（非常关键）

### ❌ 反例（无控制流设计）

```go
if cond {
    if err == nil {
        process()
    } else {
        handleErr()
    }
}
```

问题：

- 嵌套严重
- 主流程不清晰

***

### ✅ 正例（原则 + 手段）

```go
if !cond {
    return
}

if err != nil {
    return err
}

process()
```

结果：

- 扁平结构
- 错误提前退出
- 主流程清晰

***

## 九、使用时的自检标准（落地）

写完代码后检查：

1. ❓ 是否有不必要的嵌套（>2层基本有问题）
2. ❓ 错误是否第一时间 return（Fail Fast）
3. ❓ 主流程是否可以“一眼读通”（Happy Path）

满足这三点：

> 控制流设计基本合格

***

## 十、ai prompt 以及如何阅读这种控制流写的代码

prompt

```
用 Go 写代码，遵循以下规则：
- 使用 Guard Clause 处理所有异常情况（参数错误、nil、error）
- 所有错误必须立即 return（Fail Fast）
- 避免嵌套（最多2层）
- 主流程（Happy Path）必须从上到下线性可读
- 不要用 else 包裹主逻辑
```

怎么阅读：
山来直接看 happy path是否正确，然后看每个guard 的处理是否是立即return的
主要就是看是否满足这三个原则：  也就是按照卫语句模式，阅读代码

- Fail Fast（提前 return）
- Flatten（减少嵌套）
- Happy Path First（清理干扰）

## 十一 业务流控制歧义：Guard 模式与 Fallback 模式混淆

### 问题描述

在编写 `SearchWord`（单词查询）和 `Register`（用户注册）的 Service 层代码时，试图都统一套用“Guard 提前返回 + Happy Path 走到底”的线性模式。但在 `SearchWord` 中处理 `err != nil` 和 `wordModel != nil` 时逻辑变得绕杂，容易产生分支遗漏或空指针漏洞。

### 原因

这两个业务场景的流控制本质是不一样的：

1. **User (Register) 是“线性依赖流”**：操作是强依赖关系的串行。一旦遇到非预期情况（如查到已有用户，或者系统级错误），就必须抛出异常截断流程（Guard），只有一条主路通向成功（单一 Happy Path）。
2. **Word (Search) 是“降级回源流 (Fallback / Cache Aside)”**：类似缓存逻辑。本地查到了直接返回（Happy Path 1）；本地没查到（`ErrRecordNotFound`），**它不是一个需要被 Guard 掉的错误，而是触发备用路径的条件**，应该继续查远端 AI（Happy Path 2）。

把“找不到数据”当成“错误”去尝试 Guard，或者把“本地返回结果”和“AI 返回结果”混在同一个作用域里判断，就会导致代码职责不清、意图不明。

### 解决方法

针对不同业务场景采用不同的代码分流结构：

**降级回源流（如 SearchWord 可以这样改）：**

```go
// 1. 查本地一级存储，命中则直接组装返回 (Happy Path 1)
wordModel, err := repo.WordSearch(word)
if err == nil {
    return buildResponse(wordModel), nil 
}

// 2. 真正的 Guard：拦截除了 NotFound 以外的系统级崩溃（避免掩盖真异常）
if !errors.Is(err, gorm.ErrRecordNotFound) {
    return nil, err
}

// 3. 确认为 NotFound，安全触发降级，走远端 (Happy Path 2)
return utils.SearchWord(word, provider)
```

**工作流程对比：**

- **线性 Guard 流：** `校验或查询 -> 有错立刻拦截 -> 执行下一步直到成功`
- **降级 Fallback 流：** `查离得近的存储 -> 命中则提前返回 -> 是真出错了还是单纯没内容? -> 真出错了则拦截报错 -> 没内容则查备选方案 -> 返回结果`

**核心解决思路：**
无论业务流多复杂，解决问题的关键是**逐个实现 Happy Path（顺风局路径），并为每一条 Happy Path 做好专属的异常拦截（Guard）**，而不是把所有异常混在一个大 `if-else` 里去猜状态。

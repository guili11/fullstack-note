## 我们到底为什么要给并发加锁？

到底为什么不能让操作并发执行？

核心原因：**避免竞态条件**

### 什么是竞态条件呢？

先说明这里相关的两个核心前提知识：

1. **非原子性**：绝大多数的即使一行代码，也都不是原子操作，而是多个原子操作组合的操作，导致的坏结果是存在未执行完毕的中间态。这个时候没有别的线程还好说，假如有别的线程介入，就会导致数据错乱
2. **抢占式调度**：CPU 按固定时间片分配执行权，时间耗尽就会截断当前任务，切换到下一个线程，等下一次时间片分配到原线程，才能继续执行后续逻辑

### 非原子操作举例

```go
count++
```

三条原子性指令：

```
(1) 从内存读取 count 的值       →  load
(2) CPU 对这个值做 +1          →  add
(3) 把结果写回到内存             →  store
```

### 竞态条件

- **导致原因**：非原子操作（有空子）+ 抢占式调度（有人钻空子）
- **结果**：数据错乱，导致程序逻辑错误

***

## 如何避免竞态条件

所以我们避免竞态条件的两个核心点（或者说就是避免脏读）：

1. 避免非原子操作，使用原子操作
2. 使用锁机制，避免抢占式调度介入操作中间态

### 到底为什么原子性操作可以避免脏数据（竞态）呢？

**定义**：脏数据是改到一半的数据

原子性操作，要么只能读到修改前的，要么只能读到修改后的，不存在脏读问题。

注意：即使是读到修改前的，也完全符合正确的逻辑——你读到修改前的数据就证明你这条指令是我这个修改指令之前来的，所以你读到修改前的这个数据，是正确的。

那么可以发现，**原子性操作也是可以避免竞态条件的**。

***

### 梳理：避免竞态条件的方法

1. **原子操作（atomic）**：硬件级别保证 load + add + store 一气呵成，中间不可打断。性能最好，只适合简单数值操作
2. **读写锁（RWMutex）**：读锁共享不互斥，写锁独占。适合读多写少场景，性能接近 atomic
3. **互斥锁（Mutex）**：一次只有一个协程能进入临界区。性能中等，适合读写差不多的场景

> 以上 3 种是通用并发控制方案，所有语言/中间件都适用（MySQL 行锁、Redis 事务/乐观锁、Java synchronized 等，本质都是同一套思想）

注意这里是对于**共享内存冲突**的解决方案，不是并发的实现方案。

并发实现方案有 CSP、共享内存。

***

## 锁

### 第 1 步：Mutex 怎么用？

最基本的锁，先学会怎么加锁解锁、语法怎么写、什么是对应关系。

```go
var mu sync.Mutex
var count int

func add() {
    mu.Lock()
    count++
    defer mu.Unlock()
}
```

加锁保证：同一时间，只有一个协程能进入临界区执行代码，其他想进来的协程必须阻塞等待。

**临界区是什么呢？**

是一块由**同一个锁保护**的代码块，只有持有锁的协程，才能进入执行里面的代码。

（其实，核心点不是里面的代码一致，核心点是 mu 是同一个）

同一个 mutex 才互斥。

加锁保护的本质底层原理是：阻塞想要锁的地方，而不是对某个内存加锁（咋可能）——阻塞执行流。

### 第 2 步：锁锁的是什么？

理解 Mutex 锁的是"代码段（临界区）"而不是"变量本身"，这是很多人用错的根本原因。

- **临界区**：同一对 mutex 保护的代码块
- **核心注意点**：如果想保护变量，就要保证只在临界区操作变量

### 第 3 步：常见坑

- **忘记 Unlock 会怎样？** 也是死锁。其他所有想拿这把锁的协程全部永久阻塞，形成协程泄漏。其实跟内存泄漏差不多，这里就是无用协程一直存在，无法销毁。
- **什么是死锁？** 死锁就是指协程/线程无限等待
  1. 自己锁自己（单协程重复 Lock）
  2. 两个协程互相等（循环等待）——最常见，最需要处理的
  3. 忘记 Unlock

### 第 4 步：RWMutex

有了 Mutex 的基础，再学 RWMutex 就顺了。理解"读共享、写独占"是什么场景用的。

- **读锁（RLock）**：多个协程可以同时拿读锁，不互斥
- **写锁（Lock）**：写锁和所有锁（读锁 + 写锁）都互斥
  - 正在读，可以接着读，但是不能写
  - 正在写，不能接着写，也不能读

### 第 5 步：锁的粒度

锁的范围太大太小分别有什么问题，实际项目中怎么把握。

只在必要的时候锁住慢操作，避免阻塞其他协程。

例如分布式锁，但是分布式锁也不是无穷的等待，一般都有 double check。

Double Check 解决的就是「缓存击穿时，大量并发请求重复查 DB」的问题。第 1 次检查过滤掉大部分请求，锁保证只有一个人进去重建，第 2 次检查防止重复重建。

```
第 1 次检查：先看一眼缓存有没有（不加锁）
            ↓ 如果缓存没有
加锁（保证只有一个进去重建）
            ↓
第 2 次检查：再检查一次缓存有没有（防止重复重建）
            ↓ 如果还是没有
执行重建（查 DB → 写缓存）   否则直接释放锁
```

但是还是存在申请释放 n 个锁的开销，但是已经优于 DB 开销了，进一步优化是 singleflight。

# go的并发 控制 方案是什么？
go的核心理念：
主要通过 csp方案，共享内存方案辅助。

什么是csp？   
是一种并发编程模型，
核心思想是：通过通信共享数据，而不是通过共享内存来共享数据。
主要：（自动mutex）避免了共享内存的冲突问题，  发送接收机制 天然同步，利于调整协程运行顺序

核心机制？ 分为写入和读取

生产消费者模型

**写入机制**：
- 有等待的接收者（recvq 有 goroutine）→ 直接把数据给接收者，绕过缓冲区
- 缓冲区有空位 → 写入环形缓冲区
- 缓冲区满 → 当前 goroutine 封装成 sudog，挂入 sendq，进入阻塞
- 关闭的 channel 写入数据会直接 panic。

**读取机制**：
- 有等待的发送者（sendq 有 goroutine）→ 从缓冲区取或直接接收发送者的数据，**唤醒**发送者
- 缓冲区有数据 → 从环形缓冲区取
- 缓冲区空 → 当前 goroutine 封装成 sudog，挂入 recvq，进入阻塞
- 关闭的channel读，会读缓冲，没有缓冲 返回 0

4.6 Channel在什么情况下会引起内存泄漏？
Channel引起内存泄漏最常见的是引起goroutine泄漏从而导致的间接内存泄漏，当goroutine阻塞在channel操作上永远无法退出时，goroutine本身和它引用的所有变量都无法被GC回收。比如一个goroutine在等待接收数据，但发送者已经退出了，这个接收者就会永远阻塞下去。或者select语句使用不当，在没有default分支的select中，如果所有case都无法执行，goroutine会永远阻塞。出现内存泄漏

有缓冲的channel的作用是什么？
1. 解耦生产者和消费者，生产过快时不会阻塞发送方 ，异步阻塞
2. 支持批量处理，提高吞吐量
跟无缓冲的核心区别：
- 无缓冲 = 同步通信，发和收必须配对，天然用于协程同步
- 有缓冲 = 异步通信，缓冲区作为队列，适合生产消费模式

都说go的高并发性能好，是因为协程，那么go代码怎么？
其实网络服务器，在每个服务器内，每个连接都会开启一个协程，处理请求。  
严格来说是每个连接一个 goroutine，HTTP/1.1 长连接里同个连接的多个请求会复用这个 goroutine。但从开发者的角度看，每个请求的处理都在独立的 goroutine 里执行，互不干扰，handler 函数就是处理入口。

channel 的 创建 使用 关闭 运行机制？

| 知识点 | 重要性 | 说明 |
|--------|:------:|------|
| 创建/使用/关闭 | ⭐⭐⭐ | 基础操作必须掌握 |
| 有缓冲 vs 无缓冲 | ⭐⭐⭐ | 面试必问区别和适用场景 |
| 方向限定（只读/只写） | ⭐⭐ | 项目里常见，防误用 |
| 关闭后行为 | ⭐⭐⭐ | 常见考点：读关闭 channel 不会 panic |
| nil channel 行为 | ⭐⭐ | select 的高级用法，动态开关 case |
| select 多路复用 | ⭐⭐⭐ | 多 channel 监听、常用于超时控制 |
| for range 遍历 | ⭐⭐ | 遍历 channel 的标准写法，直到关闭 |
| 底层数据结构（循环队列+等待队列） | ⭐ | 了解即可，聊到实现时可以说 |

```go
// ------------------- select 多路复用 -------------------

// 基本用法：监听多个 channel
select {
case v := <-ch1:
    fmt.Println("收到 ch1:", v)
case v := <-ch2:
    fmt.Println("收到 ch2:", v)
case <-time.After(1 * time.Second):
    fmt.Println("超时")
default:
    fmt.Println("无 channel 就绪，非阻塞返回")
}

// default让 channel失去了阻塞性，但是通过time.After可以阻塞一小会，等待超时。

// 动态开关 case（nil channel 不会被选中）
var ch chan int
select {
case <-ch:               // 永久不会选中，因为 ch 为 nil
    fmt.Println("不会执行")
case <-time.After(time.Second):
    fmt.Println("只会走超时")
}

// ------------------- for range 遍历 -------------------

ch := make(chan int, 3)
ch <- 1
ch <- 2
ch <- 3
close(ch)

for v := range ch {      // 自动循环读取，直到 channel 关闭
    fmt.Println(v)        // 输出 1, 2, 3
}
// range 结束，因为 channel 已关闭
```

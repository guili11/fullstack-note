我们到底为什么要给并发加锁？   

到底为什么不能让操作并发执行？

核心原因：避免竞态条件
什么是竞态条件呢？  

先说明这里相关的两个核心 前提知识：
1. 非原子性：  绝大多数的即使一行代码，也都不是原子操作，而是多个原子操作组合的操作，导致的坏结果是 存在未执行完毕的中间态。  这个时候没有别的线程还好说，假如有别的线程介入，就会导致数据错乱 
2. 抢占式调度：cpu按固定时间片分配执行权，时间耗尽就会截断当前任务，切换到下一个线程，等下一次时间片分配到原线程，才能继续执行后续逻辑

注意：原子性操作，

非原子操作举例：
count++ 
三条原子性指令：
(1) 从内存读取 count 的值       →  load
(2) CPU 对这个值做 +1          →  add
(3) 把结果写回到内存             →  store

竞态条件是： 
导致原因： 非原子操作（有空子） + 抢占式调度（有人钻空子）
结果： 数据错乱，导致程序逻辑错误


所以我们避免竞态条件的两个核心点：     或者说就是避免脏读
1. 避免非原子操作，使用原子操作
2. 使用锁机制，避免抢占式调度，介入操作中间态

到底为什么原子性操作可以避免 脏数据（竞态）呢？
定义： 脏数据 是 改到一半的数据

原子性操作，要么只能读到修改前的，要么只能读到修改后的，不存在脏读问题
注意：即使是读到修改前的，也完全符合正确的逻辑，你读到修改前的数据就证明你这条指令是我这个修改指令之前来的，所以你读到修改前的这个数据，是正确的。

那么可以发现 原子性操作，也是可以避免竞态条件的

那么梳理一下，避免竞态条件的方法：

1. **原子操作（atomic）**：硬件级别保证 load + add + store 一气呵成，中间不可打断。性能最好，只适合简单数值操作
2. **读写锁（RWMutex）**：读锁共享不互斥，写锁独占。适合读多写少场景，性能接近 atomic
3. **互斥锁（Mutex）**：一次只有一个协程能进入临界区。性能中等，适合读写差不多的场景

> 以上 3 种是通用并发控制方案，所有语言/中间件都适用（MySQL 行锁、Redis 事务/乐观锁、Java synchronized 等，本质都是同一套思想）

4. **通道（Channel）**：Go 特有的 CSP 模型，通过传递数据所有权避免竞争。性能最差，但设计最优雅，适合协程间数据传递


锁 
### 第 1 步：Mutex 怎么用？
最基本的锁，先学会怎么加锁解锁、语法怎么写、什么是对应关系。
获取锁，解除锁
```
var mu sync.Mutex
var count int

func add() {
    mu.Lock()
    count++
    defer mu.Unlock()
}
```
加锁保证：同一时间，只有一个协程能进入临界区执行代码，其他想进来的协程必须阻塞等待。

临界区是什么呢：
是一块由 同一个锁保护的 代码块，只有持有锁的协程，才能进入 执行里面的代码
（其实，核心点不是 里面的代码一致，  核心点是  mu是同一个）

同一个mutex才互斥

加锁保护的本质底层原理是，阻塞想要锁的地方，而不是对某个内存加锁（咋可能）   
阻塞执行流


### 第 2 步：锁锁的是什么？
理解 Mutex 锁的是"代码段（临界区）"而不是"变量本身"，这是很多人用错的根本原因。
临界区：同一对mutex保护的代码块
核心注意点：就是如果想 保护变量，就要保证 只在临界区操作变量

### 第 3 步：常见坑
- 忘记 Unlock 会怎样？  也是死锁
  其他所有想拿这把锁的协程全部永久阻塞，形成协程泄漏。   其实跟内存泄露差不多，这里就是无用协程一直存在，无法销毁。
- 什么是死锁？
  死锁就是指 协程/线程 无限等待  
  1. 自己锁自己（单协程重复 Lock）
  2. 两个协程互相等（循环等待）   最常见，最需要处理的
  3. 忘记 Unlock
### 第 4 步：RWMutex
有了 Mutex 的基础，再学 RWMutex 就顺了。理解"读共享、写独占"是什么场景用的。
- 读锁（RLock）：多个协程可以同时拿读锁，不互斥
- 写锁（Lock）：写锁和所有锁（读锁+写锁）都互斥
正在读，  可以接着读，  但是不能写
正在写，不能接着写，也不能读

### 第 5 步：锁的粒度
锁的范围太大太小分别有什么问题，实际项目中怎么把握。

只在必要的时候锁住 慢操作，避免阻塞其他协程。
例如分布式锁，但是 分布式锁也不是 无穷的等待，
一般都有double check 

Double Check 解决的就是「缓存击穿时，大量并发请求重复查 DB」的问题。第 1 次检查过滤掉大部分请求，锁保证只有一个人进去重建，第 2 次检查防止重复重建。
```
第 1 次检查：先看一眼缓存有没有（不加锁）
            ↓ 如果缓存没有
加锁（保证只有一个进去重建）
            ↓
第 2 次检查：再检查一次缓存有没有（防止重复重建）
            ↓ 如果还是没有
执行重建（查 DB → 写缓存）   否则直接释放锁
```
但是还是存在 申请释放 n个锁的开销 ，但是已经由于db开销了， 进一步优化是 singleflight

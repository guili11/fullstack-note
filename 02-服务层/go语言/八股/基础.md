# 2. 进程、线程、协程区别

## 一句话核心区别

**进程是资源分配最小单位，线程是 CPU 调度最小单位，协程是用户态轻量级调度单元**。

## 分层对比标准回答

1. **进程**：独立内存、独立资源，进程间互不共享数据；切换开销最大；由操作系统内核调度；进程崩溃互不影响。
2. **线程**：隶属于进程，同进程内线程共享内存资源；内核态调度；切换开销中等；一条线程崩溃会导致整个进程崩溃；多线程并发需加锁。
3. **协程**：依附于线程，用户态自行调度；切换开销极低；单线程内串行协作执行；无需加锁；只能主动让出 CPU，不能被抢占。

系统线程切换开销主要分为 内核态切换开销 + 上下文（寄存器 + 线程栈）切换开销

## 核心三要素速记

- **资源归属**：进程独占，线程共享，协程共用线程资源
- **调度层级**：进程/线程 = 内核调度，协程 = 用户态调度    不同调度层级 的轻重不一样
- **开销大小**：进程 > 线程 > 协程

| 载体                | 隔离程度                      | 资源开销          | 调度归属  | 并发上限    |
| ----------------- | ------------------------- | ------------- | ----- | ------- |
| 进程                | 完全隔离，内存/资源互不共享，一个崩不影响其他   | 开销极大，创建销毁慢    | 内核态调度 | 很低      |
| 系统线程              | 同进程内共享堆、全局资源，单线程崩溃易连累整个进程 | 开销中等，栈空间大     | 内核态调度 | 几千～几万   |
| Go 协程 (goroutine) | 共享进程全部资源，仅栈私有             | 开销极小，初始栈仅 2KB | 用户态调度 | 几十万～百万级 |

## 什么是切换层级？

多个任务轮流占用 CPU = **任务切换**

切换时要做：**保存当前运行现场 → 切任务 → 恢复新任务现场**

**层级越高，保存的东西越多，切换越慢、开销越大**

> 我们用 goroutine，就是为了用「用户态切换」，避开「内核态切换」的性能损耗。

## 精简面试口头版

> 进程拥有独立资源，内核调度，上下文最大，隔离性最强；线程属于进程，线程间共享进程资源，内核调度，是并发的底层；协程依靠线程运行，用户态调度，切换开销最小，适合高 IO 场景。三者层级：**进程包含线程，线程包含协程**。

## IO 阻塞与切换   为什么会导致 协程阻塞（挂起）  线程阻塞（挂起）？

网络io跟文件io的区别？
网络io事件 有状态变换，可以监听。
文件io事件 没有状态变换，不能监听。

监听机制（epoll模式）   实现效果：io多路复用（线程不会被io阻塞）
网络io，可以让内核（epoll）监听网络事件。线程不用死等数据，而是去执行其他协程任务。等内核通知数据到了，线程再切回来处理。

- **IO 操作会阻塞**（等待外部资源，空出时间片，协程/线程就要切换）
- **文件 IO**：同步调用，整个线程被挂起，要执行别的协程只能开新线程
- **网络 IO**：异步调用，只有协程被挂起，线程执行别的协程，网络数据来了再执行原协程（协程小，切换开销少）

## 为什么 Go 高并发厉害（网络 IO）

高 IO 场景，尤其是网络高 IO，当协程遇到网络 IO 时，协程阻塞。作为异步调用，线程不会阻塞，线程及时切换协程，切换开销小，极大提高了 CPU 利用率。

## 常见追问

1. **Go 的 goroutine 和普通协程有什么区别？**
   - 有优化过的 GMP 调度模型
   - 工作流程：G 放入 P 的本地队列 → M 从 P 获取 G 执行 → 工作窃取平衡负载
2. **线程和协程的切换开销为什么大？**
   - 线程切换：陷入内核态，保存/恢复寄存器、页表等，约 1\~10μs；栈空间大（1\~2MB）
   - 协程切换：纯用户态，只保存少量寄存器，约 几十\~几百 ns；栈空间小（初始 2KB）
   - 差距约 **10\~100 倍**
3. **什么情况下协程也会阻塞？（区分线程阻塞和协程挂起）**
   - 协程执行系统调用（如文件 IO）时，会阻塞底层线程（文件 IO 是同步调用，线程必须等待，已进入内核态，协程不允许切换）
   - 协程等待 channel 读写、sync 包锁时，网络 IO 时会被挂起
   - Go 运行时会将被阻塞的协程迁移到其他可用线程
4. **Go 的 GMP 调度模型是什么？**
   - **G**：goroutine，包含栈、指令指针等
   - **M**：Machine，系统线程抽象
   - **P**：Processor，逻辑处理器，维护本地 goroutine 队列
   - 工作流程：G 放入 P 的本地队列 → M 从 P 获取 G 执行 → 工作窃取平衡负载
5. **协程之间如何通信？**
   - 推荐：**channel**（"不要通过共享内存来通信，要通过通信来共享内存"）
   - 也可：sync 包（Mutex、WaitGroup 等），适用于需要精确控制的场景
6. 为什么说goroutine很轻？
   用户态+2kb栈
   goroutine 是 用户态调度 ，不依赖内核，而且本身栈空间很小2kb，切换成本远低于线程

## 踩坑/易错点

- ❌ 误区：协程不需要加锁 → ✅ 多协程访问共享变量仍需同步机制（锁/channel/atomic）
- ❌ 误区：协程可以被抢占 → ✅ Go 1.14 之前只能协作式让出，1.14+ 才支持异步抢占
- ❌ 误区：协程越多越好 → ✅ 过多协程会导致调度开销增加、内存占用过大（每个 goroutine 初始栈 2KB）
- ❌ 误区：goroutine 泄漏不影响程序 → ✅ 泄漏的 goroutine 不会被 GC 回收，会导致内存泄漏
- ❌ 误区：协程是操作系统调度的 → ✅ 协程是用户态调度，由语言运行时（如 Go runtime）自行管理
- ❌ 误区：线程崩溃只影响自己 → ✅ 线程崩溃会导致整个进程崩溃，同进程内所有线程都会终止

# 3. make 和 new 的差异

| 维度          | new                  | make                   |
| ----------- | -------------------- | ---------------------- |
| 设计定位        | 通用内存分配器              | 特定引用类型专用初始化器           |
| 适用类型        | 任意类型（值类型/引用类型均可）     | 仅 slice/map/channel 三种 |
| 核心动作        | 分配内存 + 置零值           | 分配内存 + 初始化底层数据结构       |
| 返回值         | 指向零值内存的指针（\*T）       | 已初始化的实例本身（T）           |
| 为什么返回指针/非指针 | 通用设计，需通过指针让用户操作分配的内存 | 目标类型内部已含指针，返回实例更简洁易用   |

<br />

面试回答：make ：只用于 slice、map、channel， 分配内存 + 初始化底层数据结构 ，返回的是 实例本身 （不是指针）

new ：通用分配， 只分配内存、置零值 ，返回的是\*\*指向零值的指针 T \*

## 注意事项

- ❌ `new(T)` 返回的是**指针**，`make(T)` 返回的是**实例**
- ✅ `make` 只能用于 **slice、map、channel**，其他类型用 `make` 会编译报错
- ✅ `new` 分配的内存会被**清零**（int→0, string→"", 指针→nil）
- ✅ `make(slice, len, cap)` 可以指定长度和容量，`make(map, hint)` 可以指定初始容量（性能优化）
- ❌ 用 `new` 创建 slice/map 得到的是**零值指针**，直接使用会 panic，必须再初始化
- ✅ 实际开发中 **90% 场景用** **`make`**，`new` 很少用到（通常用字面量 `&T{}` 替代）

# 4. 数组和切片的区别

| 对比维度  | 数组 \[N]T             | 切片 \[]T                 |
| ----- | -------------------- | ----------------------- |
| 类型定义  | 长度是类型一部分，长度不同就是不同类型  | 无固定长度，长度不属于类型，只看元素类型    |
| 数据本质  | 值类型                  | 引用类型                    |
| 内存结构  | 占用整块连续固定内存           | 本身是结构体，存指针、长度、容量，指向底层数组 |
| 长度特性  | 长度固定，声明后无法修改         | 长度动态，可增删元素改变长度          |
| 赋值拷贝  | 整体完整拷贝一份新数据，互不干扰     | 仅拷贝切片结构体，共用同一份底层数组      |
| 扩容能力  | 不支持扩容，满了无法再加元素       | 支持自动扩容，容量不足自动开辟新数组      |
| 初始化方式 | var a \[5]int、字面量初始化 | 字面量、make 创建，日常优先 make   |
| 函数传参  | 传值拷贝，函数内修改不影响原数组     | 传切片结构体副本，修改会影响底层原数据     |
| 零值状态  | 零值所有元素默认初始化为零值       | 零值为 nil，无底层数组           |
| 使用场景  | 固定长度、少量静态数据          | 动态数据、业务开发绝大多数场景         |

## 指针使用原则

- 数组本身就是值，slice 本身是指针结构体
- 修改数组 → 用指针数组 `*[N]T`
- 修改切片 → 直接传 slice 本身即可

## 值传递 vs 引用传递

> 所有参数传递本质全是拷贝，没有例外；区别只在于：拷贝的是数据本体，还是指针地址

## slice 的核心使用价值

**动态长度 + 轻量传递 + 内置函数支持**

# 5. for range 的使用

for range - 迭代循环，核心作用是**简化对集合的遍历操作**，可以直接遍历数组、切片、map、字符串、通道等类型

```go
// 遍历数组/切片/字符串：index 是索引，value 是元素值
for index, value := range collection {
    // 循环体
}

// 遍历 map：key 是键，value 是值
for key, value := range mapData {
    // 循环体
}

// 遍历通道：仅返回通道内的值（通道关闭后循环自动退出）
for value := range channel {
    // 循环体
}
```

## 核心原则

遍历集合关注的核心：**read 还是 write？**

Go 设计 for range 的初衷是「安全遍历读取」，拿到的永远是元素的**副本拷贝**（value），修改副本 ≠ 修改原集合。

**修改集合必须用 index/key：**

```go
// 数组/切片：利用 index 修改
for i := range slice {
    slice[i] = newValue
}

// map：利用 key 修改
for k := range m {
    m[k] = newValue
}
```

## 注意事项

1. map 遍历顺序随机，不能在遍历 map 时修改 map
2. 遍历 channel 时，需要生产结束后主动关闭 channel，否则无限循环
3. Go 1.22 之后，每次迭代的 value 都是新变量，有各自的地址，实现闭包正确捕获

## 闭包捕获问题

```go
// Go 1.22 之前：所有迭代共用同一个 value 变量
// ❌ 闭包捕获的是同一个地址
for _, v := range slice {
    go func() {
        fmt.Println(v)  // 所有 goroutine 打印最后一个值
    }()
}

// Go 1.22 之后：每次迭代创建新变量
// ✅ 每个 goroutine 捕获各自的 v
for _, v := range slice {
    go func() {
        fmt.Println(v)  // 正确打印各自值
    }()
}
```

### 为什么循环结束后协程才执行？

- `go` 关键字只是「提交任务」，不是「立刻执行」
- 主协程循环执行特别快，然后才轮到协程

### 协程传参 vs 闭包捕获

- **协程传参** = 启动时立刻拷贝、立刻传递
- **闭包捕获** = 执行前记忆变量地址，执行时才去读取变量

## 最佳实践

> 使用 `go func(val int) { fmt.Println(val) }(v)` 开启协程，避免因 Go 版本导致的闭包捕获问题

# 6. 如何高效拼接字符串

| 方式                | 场景               | 特点                        |
| ----------------- | ---------------- | ------------------------- |
| `+`               | 单次纯字符串拼接         | 简单直接，但循环/大量拼接性能差（每次生成新对象） |
| `fmt.Sprintf`     | 字符串 + 数字/多类型混合拼接 | 灵活方便，但底层用反射，高频调用有性能损耗     |
| `strings.Builder` | 循环/大量拼接（性能首选）    | 预分配内存无多余拷贝，Go 官方推荐的高效方案   |

**口诀**：少量纯串用 `+`，混合拼接 `Sprintf`，循环大量 `Builder`

# 7. defer 的执行顺序与使用场景

## 执行顺序

**先进后出（栈结构）**

```go
defer fmt.Println("1")
defer fmt.Println("2")
defer fmt.Println("3")
// 输出: 3 2 1
```

## 使用场景

**管理成对性资源**，以及少数 GC 无法管理的资源（衍生 ctx 上下文）。

> **注意区分**：GC 管理的是内存泄漏，defer 管理的是资源泄漏。资源指的是系统资源（如数据库连接、文件等），和内存没关系，GC 管理不了。

**系统资源（如连接/文件）需显式管理。程序无法自动判断资源是否仍被使用（例如长连接空闲），必须由开发者手动释放。**

## 经典示例

```go
// 1. 数据库查询结果集
rows, err := db.Query("SELECT ...")
defer rows.Close()  // 不关会耗尽连接池（gorm 自动完成）

// 2. HTTP 响应体（客户端场景）   跟数据库临时查询一样  （前端不需要管理，浏览器控制，  服务端需要管理）
resp, err := http.Get(url)
defer resp.Body.Close()  // 不关会泄漏连接

// 3. 文件操作
file, err := os.Open("data.txt")
defer file.Close()  // 不关会耗尽文件描述符

// 4. 网络连接
conn, err := net.Dial("tcp", "host:port")
defer conn.Close()  // 不关会占用端口

// 5. 互斥锁
mu.Lock()
defer mu.Unlock()  // 不关会导致死锁

// 6. Context 释放（这是内存管理）
ctx, cancel := context.WithTimeout(ctx, 1000)
defer cancel()
```

## panic 异常恢复

**核心机制：panic 抛出异常 → defer recover 捕获恢复**

```go
func safeFunc() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("捕获到 panic:", r)
            // 可以记录日志、返回错误等
        }
    }()
    
    // 可能 panic 的代码
    panic("出错了！")
}
```

### 关键规则

- ✅ **recover 必须在 defer 中调用**，直接调用无效
- ✅ **recover 只能捕获当前 goroutine 的 panic**，跨 goroutine 无效
- ✅ **panic 后只有 defer 会执行**，后续代码不执行
- ✅ **recover 后程序继续执行**，不会崩溃
- ❌ **不要用 panic/recover 替代 error 处理**，只用于真正异常场景

### 典型场景

```go
// 1. Web 中间件：防止单个请求 panic 导致服务崩溃
func middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("请求 panic: %v", r)
                http.Error(w, "Internal Server Error", 500)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

// 2. 并发任务：防止单个任务 panic 影响其他任务
func runTasks() {
    var wg sync.WaitGroup
    for _, task := range tasks {
        wg.Add(1)
        go func(t Task) {
            defer wg.Done()
            defer func() {
                if r := recover(); r != nil {
                    log.Printf("任务 %s panic: %v", t.Name, r)
                }
            }()
            t.Execute()
        }(task)
    }
    wg.Wait()
}
```

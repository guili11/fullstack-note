# Go Context 上下文 极简复习笔记（完全贴合你的思路整理）

## 一、需求引入：为什么需要 ctx

1. **最初痛点**
   函数多层调用时，需要传递请求标识、用户信息、超时限制等内容；
   单纯靠普通函数参数传递，参数越来越多，冗余繁琐、维护成本极高。

2. **初步想法**
   既然多处都要用这些信息，不如定义**全局变量**统一存取，所有函数、协程直接访问使用。

3. **全局变量致命问题**
- 无法管控变量**生命周期**，请求结束无法及时清理

- 多请求并发场景下，全局数据互相覆盖，数据错乱

- 无法实现统一取消、统一超时控制
1. **最终解决方案**
   Go 官方提供 `context.Context` 上下文，专门用来**绑定单次请求链路**，统一存放链路信息、统一管控生命周期，替代杂乱传参与不安全全局变量。

## 二、Context 本质

1. **本质**
   一块依附于**单次请求链路**的只读内存容器，以**父子层级**形式存在，上层上下文信号自动向下传递。
2. **官方定义**
   跨函数边界、跨 Goroutine，跨rpc，传递**控制信号**与**请求域共享数据**的标准机制。

都是传参实现的，核心得保证，在请求链路中就那一个ctx

1. **核心解决三大问题**
- 取消控制：上游终止请求，下游全部停止执行
- 超时控制：整条链路统一限时，防止服务卡死阻塞
- 链路透传：传递 TraceID、用户信息、请求标识等轻量数据

## 三、两大核心范围区分（你重点总结）

1. **Go 原生 ctx**
   作用域仅限**单机内部单次请求**，只在当前服务内流转，**不能跨服务全局通用**。
2. **分布式全局唯一标识**
   不是 ctx 本身，是**存放在 ctx 内部的 TraceID**；
   跨微服务通过请求头传递 TraceID，实现全链路追踪。

## 四、基础上下文分类（快速记）

1. `context.Background()`
   业务入口**根上下文**，无超时、无取消，所有请求链路的起点。  整个请求链路只能使用一次
2. `context.TODO()`
   临时占位使用，不确定上下文时临时填充，正式业务禁止使用。
3. 常用衍生子上下文   f(ctx,...)  必须通过父ctx衍生，本身不能作为根ctx
- `WithCancel`：手动触发取消信号
- `WithTimeout`：最常用，设置自动超时时间
- `WithDeadline`：指定具体时间点超时
- `WithValue`：存放链路轻量标识数据

## 五、核心使用规则（完全按你的理解整理）

### 1. 初始化规则

- 单机接口入口：基于 `Background` 创建**带超时的业务 ctx**
- **跨服务调用**：直接复用上游传递过来的 ctx，禁止重新新建重置，避免链路断裂

### 2. 传递规范

1. 统一放在**函数第一个入参**，逐层向下透传
2. 必须透传至：网络请求、文件IO、数据库操作、RPC 调用
3. 原理：这类底层阻塞操作**不受Go协程用户态调度控制**，直连操作系统内核；只有传入 ctx，才能让Go实现超时终止、主动取消
4. 正确写法：**耗时操作自身绑定 ctx**（如 `db.WithContext(ctx)`），**不要等操作执行完再判断 ctx 状态**

### 3. 信号监听

1. **`ctx.Done()`**：**阻塞监听通道** → 只用于 **协程、死循环、长连接** 这种需要**持续等待信号**的场景
2. **`ctx.Err()`**：**非阻塞查状态** → 用于 **普通业务代码、DB/HTTP/RPC 调用后**，直接判断是否超时 / 取消

**你日常写业务（Handler/Service/Repo）：只用 `ctx.Err()`**

### 4. cancel 函数规范   一定要及时释放衍生ctx

使用衍生 ctx 拿到 cancel 后，必须 `defer cancel()`，及时释放上下文资源，避免内存泄漏（内存浪费）。   全程ctx，不需要释放，生命跟随整个请求流程，结束，自动释放

## 六、标准业务流转流程（实习开发通用）

1. **Handler 接口层（顶层）**
   入口创建**接口粒度全局超时 ctx**，定义整条请求最大执行时长，注册 cancel 销毁函数。
2. **Service 业务层**
   只接收 ctx、原样透传，**不私自新建上下文**，不修改链路控制规则。
3. **Repo/工具类/第三方调用层**
   所有数据库、Redis、HTTP 耗时操作，全部绑定传入的 ctx；
   操作触发后自动响应超时/取消，出现上下文错误**向上抛出**。
4. **顶层统一处理**
   Handler 统一捕获上下文超时、取消错误，封装标准化响应返回前端。

## 七、两种超时控制粒度

1. **接口全局超时（推荐主流）**
   在 Handler 统一创建超时 ctx，**整条请求链路共用同一个超时限制**，保障用户侧请求可终止。
2. **局部操作粒度超时**
   不在入口创建，在单独数据库调用、第三方接口调用前，单独创建短期超时 ctx，精准限制单个操作耗时。

## 八、为什么超时 ctx 优先创建在 Handler 层

1. 贴合真实业务：用户主动取消请求、网关超时，可从上到下快速感知
2. 统一管控整条业务链路，避免局部超时混乱，保证请求整体可用性
3. 区分：接口整体超时 ≠ 服务内部单个方法超时

## 九、高频禁止错误用法

1. 禁止用 `WithValue` 存放大量业务实体、接口入参
2. 禁止长期全局持有 ctx，脱离单次请求链路
3. 禁止多层调用随意丢弃 ctx，导致链路追踪、超时控制失效 ，禁止 超过一次使用ctx.Background()
4. 禁止协程内部新建无关 ctx，脱离主请求控制
5. 禁止耗时操作执行完毕后再校验 ctx 状态

## 十、终极速记口诀

传参繁琐造 ctx，单次请求做载体；
父级信号向下传，取消超时统一管；
入口创建定时长，层层透传不重造；
IO 网络绑定它，内核阻塞也可控；
本地链路靠 ctx，分布式追踪靠 ID。

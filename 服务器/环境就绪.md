├─ Phase A: Pre-Run (环境就绪)
│  ├─ ⭐ 环境变量加载 (Env)
│  │  ├─ 任务：定义服务运行的基础身份标识（实例 ID、环境、Region）
│  │  └─ 方案：os.Getenv / viper / K8s Downward API
│  ├─ ⭐ 配置源读取 (Provider)
│  │  ├─ 任务：从统一的配置中心或本地文件获取业务配置
│  │  └─ 方案：本地 yaml / viper 多源合并 / Nacos SDK / Etcd Watch
│  ├─ ⭐ 配置校验 (Validator)
│  │  ├─ 任务：启动前拦截缺失或错误的配置项，防止带着错误配置运行
│  │  └─ 方案：go-playground/validator / json-schema / 自定义 validate
│  └─ 🚀 密钥管理 (Secret)
│     ├─ 任务：数据库密码、API Key 等敏感信息不写死在配置文件或代码中
│     └─ 方案：Vault / KMS / Kubernetes Secret 环境变量注入

## 工作流程

一句话核心：

**Env = 启动选环境，运行期不变；Provider = 运行期调参，需要热更新**

| <br /> | Env（环境变量）                  | Provider（配置源）     |
| ------ | -------------------------- | ----------------- |
| 变更时机   | **启动时一次性加载，运行期只读**         | **运行期动态更新，支持热加载** |
| 关注层级   | 基础设施层（部署环境标识）              | 业务层（业务运行参数）       |
| 作用     | 标识当前部署环境（dev/staging/prod） | 定义业务逻辑所需的运行时参数    |

具体来说：程序先通过 `os.Getenv("ENV")` 拿到当前环境标记（dev/staging/prod），然后根据这个值去读**对应环境的业务配置文件**（如 `config-dev.yaml` 或 Nacos 的 dev 命名空间），这些配置文件中定义的就是上表中的数据库地址、回调地址、日志级别等**业务层的运行时参数**。

Env 本身不包含任何业务信息，它只是一个\*\*"索引键"\*\*，用于在配置源中找到正确的配置集。

## 配置分类

Provider 读到的配置文件又分为两类：

| 配置类型                       | 说明                  | 示例              |
| -------------------------- | ------------------- | --------------- |
| **环境配置（dev/staging/prod）** | 按部署环境区分，不同环境值不同，静态的 | 数据库地址、回调地址、日志级别 |
| **服务配置（service）**          | 同环境下业务调参，热更新的       | 限流阈值、功能开关、超时时间  |

环境配置跟随部署环境变化，部署时选哪套就是哪套；服务配置在同一环境下独立变更，不影响部署。

## 举个例子

你写了一个支付服务，部署在 3 个环境：

| <br /> | dev      | staging | prod |
| ------ | -------- | ------- | ---- |
| 数据库    | 本地 MySQL | 测试库     | 线上库  |
| 支付宝回调  | 沙箱地址     | 沙箱地址    | 真实地址 |
| 日志级别   | debug    | info    | warn |
| 告警     | 不告警      | 通知开发    | 电话值班 |

同一份编译出来的二进制，程序不可能自己猜"我现在在哪个环境"——必须靠外部告诉它。

```go
func main() {
    env := os.Getenv("ENV")  // 基础设施注入

    switch env {
    case "dev":
        db = connect("localhost:3306")
    case "prod":
        db = connect("生产地址")
    }
}
```

## 总结

- **Env**：部署时选边（dev / staging / prod），选完就定了，不改了。它不关心业务，只告诉程序"你在哪"
- **Provider**：同一边（比如 prod）下，业务参数随时要调——限流阈值、功能开关、连接串等，改完要生效但不能重启

如果 Env 放到配置中心里，改个环境还得去热更新配置，但部署时本来就能决定的事，何必绕一圈。

## Env 实现方案

- **os.Getenv** — 最直接，启动时逐 key 读取，适合 key 少或临时调试
- **viper.BindEnv** — 将环境变量绑定到配置结构体，统一管理入口
- **K8s Downward API** — 通过文件系统注入 Pod 元数据（PodIP/Namespace等），适用于 K8s 部署场景

## Provider 实现方案

- **本地 yaml** — 读取本地配置文件，简单直接，适合单机开发
- **viper 多源合并** — 支持本地文件 + 环境变量 + 远程配置多层覆盖，优先级可配
- **Nacos SDK** — 通过 SDK 拉取远端配置，支持长轮询监听变更
- **Etcd Watch** — 通过 Watch 机制监听 key 变化，实现配置热更新
